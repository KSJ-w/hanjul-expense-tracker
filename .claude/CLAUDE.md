# CLAUDE.md — 한줄 가계부 (hanjul-expense-tracker)

> 이 파일은 작업 지원 지침이다. **요구와 시험의 권위는 `docs/` 의 요구 문서에 있다.**
> 여기 적힌 것과 문서가 어긋나면 문서가 이긴다. 구조가 실제로 어떤지는 코드가 이긴다.
>
> **작업을 끝내기 전에 §9 를 반드시 읽는다.** 코드 → TC → 검증 → 문서 역반영 →
> 재검증이 한 작업 단위다. `npm run verify` 가 통과하기 전에는 완료가 아니다.

## 1. 프로젝트 개요

**달력이 중심**인 개인용 가계부. 기록 입력은 **화면 하단의 프롬프트 바 하나**이고,
날짜를 누르면 그날의 상세 창이 열린다. 하단 바에 적어 보내면 '저장 전 확인'이 뜬다.
**사람이 한 번 확인해야** 기록이 된다. 혼자 쓰는 도구이며 로그인이 없다.
화면은 **달력·통계·내역·설정** 네 목적지다(ADR-020·ADR-030). 한 목적지는 한 목적만 맡는다.
화면에서 분류는 **태그**로 부른다(ADR-031).

- Next.js 16 (App Router, Turbopack) · React 19 · TypeScript
- 저장: `node:sqlite`(내장) — 네이티브 빌드가 없다. 파일은 `data/expense.db`
- 화면: HeroUI v3 + Tailwind v4 · 차트: Recharts 3
- 시험: Vitest. TC 대조는 `node test/generate-report.mjs`

## 2. 아키텍처 원칙 (Invariants — 최우선 준수)

다른 규칙과 충돌하면 이것을 먼저 지킨다. 근거는 `docs/sdd/SDD.md` §2다.

1. **외부로 나가는 호출은 `src/lib/interpret/gemini.ts` 에만 존재한다.**
   다른 어디에도 `fetch` 를 쓰지 않는다. `test/boundary.test.ts` 가 소스를 훑어 검사한다.
   여기를 어기면 `FR-ENTRY-15`(해석 외 전송 금지)를 판정할 근거가 사라진다.
2. **확정 기록은 `createRecord()` 를 거쳐서만 생긴다.** 후보(`candidates`)와 기록(`records`)은
   다른 표다. 확인 동작 없이 `records` 에 넣는 경로를 만들지 않는다(`FR-ENTRY-05`).
3. **집계·조회는 `records` 만 읽는다.** 후보를 합계에 넣지 않는다. 모든 조회에
   `deleted_at IS NULL` 이 붙는다.
4. **분류 삭제는 보관 처리다.** `categories.archived_at` 을 채울 뿐 행을 지우지 않는다.
   행을 지우면 그 분류에 속했던 기록의 귀속이 끊겨 `NFR-CAT-01` 이 깨진다.
5. **자동 배정 분류는 언제나 사용자 분류 집합의 원소다.** 없는 분류를 만들어 붙이지
   않는다. 마땅한 것이 없으면 `null`(미확정)로 둔다(`FR-CAT-06`).
6. **빈 결과를 부재로 표시하지 않는다.** "찾지 못함"과 "없었음"은 다르다(`FR-VIEW-07`).
   조회 함수는 `{ items, noMatch }` 를 돌려준다. 금지 대상은 **부재를 단정하는
   표현**이지 빈 자리가 아니다 — 아무 말도 하지 않는 것은 이 금지에 걸리지 않는다
   (ADR-029). 무언가 적을 때는 `EmptyNote` 를 쓰고, 그것은 **기록**이 없다고만
   말한다. 설명 문장이 아니라 낱말이 그 구분을 지킨다.
   조건을 걸어 찾는 화면(내역)에서는 **반드시 적는다** — 거기서 아무 말이 없으면
   '조건에 맞는 것이 없다'와 '거래가 없었다'가 구별되지 않는다.

## 4. 코딩 규칙

- **저장소 함수는 마지막 인자로 `db: DatabaseSync = getDb()` 를 받는다.** 시험이 임시 DB 를
  넘길 수 있어야 한다. 이 규칙을 어기면 그 함수는 시험할 수 없다.
- **실패를 예외로 던지지 않는다.** `{ ok: false, reason }` 을 돌려준다. 화면이 사용자에게
  무슨 일이 있었는지 말해야 하므로, 사유가 타입으로 남아야 한다.
- **날짜에 `toISOString()` 을 쓰지 않는다.** UTC 로 바뀌어 한국 시간대에서 하루 밀린다.
  `toISODate()` 를 쓴다.
- **금액은 정수(원)다.** 부동소수를 쓰지 않는다.
- 사용자에게 보이는 문구는 한국어로, "찾지 못했다"와 "없었다"를 섞지 않는다.
- **화면이 스스로를 해설하는 문장을 상시로 붙이지 않는다(ADR-031).** '이 주는 아직
  지나지 않았어요'·'같은 눈금으로 그렸어요' 같은 것을 **요청받기 전에는 넣지 않는다.**
  읽어야 할 것은 값이고, 값 옆에 값에 대한 말을 두면 그 말부터 읽게 된다.
  꼭 알려야 하는 상태는 문장이 아니라 **표시**로 만든다.
- **화면에서는 '분류'가 아니라 '태그'다(ADR-031).** 요구 문서·코드·DB 는 계속
  `category`·'분류'를 쓴다. 둘의 대응은 SRS §1.4 용어집 한 곳이 갖는다.
  값이 없을 때는 '미분류'가 아니라 **'태그 없음'** 이다.
- 주석은 "무엇을"이 아니라 **"왜 이렇게 했는가"**를 적는다. 특히 요구 번호를 남긴다.

## 5. 계약 표

| 표면 | 무엇 | 비고 |
|---|---|---|
| `stageFromInput(text, imageDataUrl?)` | 입력 → 기록 후보 세우기 | 확정하지 않는다 |
| `searchTurnAction(text)` | 조회 문장 → **덩어리마다** 조건 + 결과 기록 | 알아들은 것이 없으면 `ok:false` — 조회하지 않는다 |
| `interpretQuery(input)` | 조회 문장 → `{ parts }` | 몫마다 조건·알아들은 조건·이름. `parts` 가 비면 '아무것도 알아듣지 못함'이다 |
| `confirmCandidateAction(id)` | 후보 → 확정 기록 | 미확정 항목 있으면 실패 사유로 알린다 |
| `GET /api/export?images=0\|1` | 반출 묶음(JSON) | 기본은 이미지 포함(NFR-VIEW-03) |
| `GET /api/export/csv` | 표 계산용 CSV | **복원용이 아니다** |
| `GET /api/image/[id]` | 근거 이미지 | 기기 안 파일을 돌려줄 뿐 |
| 라우트 | `/`(달력) · `/dashboard`(통계) · `/search`(내역) · `/settings`(설정) | 목적지를 늘리거나 줄이기 전에 ADR-020 을 먼저 고친다 |
| `/dashboard?p&d&n` | 통계의 주소 | `p` 기간 종류 · `d` 앵커 날짜 · `n` 추이에서 견주는 개수(ADR-037). 링크를 만들 때 셋을 함께 싣는다 |
| `<QueryForm action className>` | 조건만 바꾸는 GET 폼 | 전송을 가로채 `router.push(..., { scroll: false })` 로 옮긴다. 빈 칸은 주소에 싣지 않는다 |
| 예산 | `repo/budgets` · `setBudgetAction` | 화면은 ADR-014 로 내렸다. 계층은 살아 있고 `FR-VIEW-08`·`FR-VIEW-09` 도 유효하다 |
| `weekOfMonth(iso)` · `shiftPeriod(type, anchor, delta)` | 기간의 이름과 이동 | '몇 주차'는 **그 달의 1일이 든 주가 1주차**다(ADR-030) |
| `holidayName(iso)` · `isRedDay(iso)` | 그 날이 공휴일인지와 이름 | 표는 기기 안에 있다. 밖에 물어보지 않는다(ADR-022) |
| `<RecordDialog date record?>` | 기록 창 | `record` 가 있으면 고치는 창, 없으면 새로 적는 창. 날짜 칸·방향 바·X 가 없다 |
| `<Select options groups? name?>` | 고르는 칸 | `name` 을 주면 숨은 input 으로 값을 보낸다(GET 폼용) |
| `<AmountInput value onChange>` | 금액 칸 | 값은 자릿점이 찍힌 문자열로 오간다. 받는 쪽이 걷어낸다 |
| `InterpretProvider` | 해석 수단 계약 | 새 수단은 `interpret`·`interpretQuery` 둘을 구현하고 `PROVIDERS` 에 넣는다 |

## 7. 정책·결정 로그

되돌려지면 안 되는 결정과, **이미 반증된 대안**이다. 전체는 `docs/sdd/SDD.md` §3(ADR).

- **금액의 부호는 방향이 먼저다(ADR-021).** 이 제품의 금액은 늘 양수 크기이고
  방향을 따로 들고 있다. `amount > 0` 을 `direction` 보다 먼저 보면 지출에 '+' 가
  붙는다 — 같은 기록이 달력에서는 −8,500, 내역에서는 +8,500 이었다(실제로 겪음).
  계약은 `TC-VIEW-32` 가 지킨다.
- **상단에 입력 카드를 만들지 않는다(ADR-021).** 기록 입력은 하단 프롬프트 바 하나다.
  설명을 더하려고 제목·안내·버튼 줄을 상시로 두면 달력이 첫 화면에서 밀려난다
  (실제로 겪음 — 1280×720 에서 달력 시작 y 564px, 390px 에서 734px).
  설명은 없애는 것이 아니라 **필요한 순간**(첨부·실패·저장)으로 옮긴다.
- **하단에 내비게이션을 고정하지 않는다(ADR-021).** 하단은 입력의 자리다.
- **강조색을 더 옅게 가져가지 않는다(ADR-021).** 지금 #6366e0 은 흰 글자가
  4.66:1 로 읽히는 선이다. 더 파스텔로 만들면 전송 화살표와 오늘 날짜 숫자가
  읽히지 않는다. 파스텔 인상은 **면**(`--accent-container`)으로 만든다.
- **달력을 판으로 감싸지 않는다(ADR-021).** 격자가 이미 테두리를 가진다. 감싸면
  하단 프롬프트와 좌우 끝이 어긋난다(실제로 겪음 — 37px). 프롬프트와 본문은
  **같은 상자**(`max-w-[1056px] px-4 sm:px-6`)를 써야 끝이 맞는다.
- **날짜 팝업의 크기를 내용에 맡기지 않는다(ADR-021 → ADR-028).** 같은 자리를
  눌러도 매번 다른 크기의 창이 뜨면 다음에 누를 곳의 위치가 바뀐다.
  **최소 높이로는 이것이 지켜지지 않았다** — 기록이 다섯을 넘는 날에는 그만큼
  창이 자랐다(실제로 겪음). 목록을 **다섯 줄 높이(244px)로 고정**하고 그보다
  많으면 목록 안에서 굴린다. 줄 하나가 48px 이라는 전제가 숫자로 박혀 있으므로
  줄의 구성을 바꾸면 244 도 함께 고친다.
- **없는 값을 낱말로 채우지 않는다(ADR-028).** 적은 내용이 없는 기록은
  '내용 없음'이 아니라 흐린 `-` 로 자리만 지킨다. 없다는 사실을 낱말로 적으면
  **내용이 있는 줄보다 오히려 눈에 걸린다** — 목록에서 눈이 찾는 것은 내용과
  금액이다. 다만 `-` 는 낭독기에 뜻이 없으므로 `aria-label` 이 반드시 따라다닌다.
- **색을 더하기 전에 그 색이 무슨 뜻인지 말할 수 있어야 한다(ADR-017).**
  적·녹은 거래 방향이고 금액에만 붙는다. 파랑은 지금 있는 곳과 주 동작이다.
  `--cat-*` 는 차트 안에서만 쓴다. 그 밖의 전부는 중립이다.
- **뜻을 색으로만 전달하지도 않는다(ADR-020).** 지출·수입은 색과 함께 부호(−/+)와
  낱말로 알린다. 흑백 화면에서도 구별되어야 한다.
- **달력의 날짜 숫자에서 붉은색은 '쉬는 날'이다(ADR-022).** 거래 방향의 붉은색과
  값을 나눠 둔다(`--holiday` #c62828 ≠ `--dir-expense` #bb3e50). 같은 붉은색을
  쓰면 한 화면에서 '지출'과 '휴일' 둘을 뜻하게 된다 — ADR-017 이 요일 색을
  기각했던 이유가 그것이다. 공휴일은 **이름을 함께 적어** 색만으로 지지 않는다.
  다른 달의 날짜에는 붉은색을 주지 않는다 — 그 칸이 먼저 말할 것은 '이 달이 아니다'다.
- **공휴일을 밖에 물어보지 않는다.** 공휴일 API 를 부르면 §2 불변조건 1 이 깨진다.
  `domain/holiday.ts` 가 표를 들고 있고, 음력에서 오는 셋(설날·추석·부처님오신날)만
  해마다의 양력 날짜를 적어 둔다. 표가 아는 해는 2024~2032 다. 표가 틀리면 화면이
  조용히 틀리므로 `test/view.holiday.test.ts` 가 해마다의 값을 못 박는다.
- **설·추석 연휴는 토요일과 겹쳐도 대체공휴일이 없다.** 일요일·다른 공휴일과 겹칠
  때만 생긴다. 어린이날과 삼일절·광복절·개천절·한글날·부처님오신날·성탄절은
  토·일 둘 다 대상이고, 신정과 현충일은 대상이 아니다. 한 날에 둘이 겹쳐도 대체는
  하루뿐이다 — 2025-05-05 는 어린이날이자 부처님오신날이었지만 대체는 5/6 하루였다.
- **아이콘은 목록 줄에서만 쓴다(ADR-023 → ADR-027 이 범위를 줄임).** 줄이 다섯이면
  글자 버튼이 열 개가 되어 읽어야 할 이름과 금액보다 넓어진다(분류 관리에서 실제로 겪음).
  줄은 자리가 없으므로 아이콘이 맞다. 아이콘에는 이름이 없으므로 **`IconButton` 을
  거친다** — `label` 이 필수 인자라 이름 없는 아이콘 버튼을 만들 수 없다.
- **창 바닥의 동작은 낱말이다(ADR-027).** 바닥에는 낱말을 넣을 자리가 있고,
  아이콘만 두면 이름이 없어 뜻이 추측이 된다(NN/g). 체크 표시 하나는 그것이
  '저장'인지 '확인'인지 말하지 않는다.
- **바닥의 차례는 [되돌릴 수 없는 것] … [취소] [확인]이다(ADR-027).**
  확인하는 동작이 맨 오른쪽, 취소가 그 왼쪽(Material Design 3 · PatternFly).
  되돌릴 수 없는 동작은 **반대쪽 끝**으로 뗀다 — 습관대로 오른쪽을 눌렀을 때
  닿지 않아야 한다(GitLab Pajamas · PatternFly).
- **고치는 칸이 있는 창에는 X 를 두지 않는다(ADR-027).** X 는 '그냥 닫기'로도
  '적은 것을 버리기'로도 읽힌다(NN/g, 'Cancel vs Close'). 그런 창은 바닥에
  '취소'를 낱말로 두고 같은 뜻의 닫는 길을 둘 두지 않는다(`Dialog` 의 `hideClose`).
  읽기만 하는 창(날짜 상세)과 닫아도 값이 남는 창(저장 전 확인)은 X 를 유지한다.
- **삭제에 확인 창을 겹치지 않는다(ADR-027).** 확인과 되돌리기 중 하나면 되고,
  이 제품에는 되돌리기가 있다(ADR-019). 그래서 **되돌리기 줄이 반드시 살아 있어야
  한다** — 그것이 사라지면 되돌릴 길이 없다.
- **저장에 진한 강조색을 채우지 않는다(ADR-023).** 창 바닥 전체를 보라로 칠하면
  그것이 화면에서 가장 큰 소리가 된다. 저장은 소리를 질러야 하는 동작이 아니다.
  확인하는 동작은 어느 창에서나 옅은 면(`btn.soft`)으로 같은 옷을 입는다.
  강조색은 아무 데나 쓰는 테마색이 아니라 **뜻이 있는 자리**에만 쓴다(ADR-017).
- **창 바닥의 실선은 본문이 실제로 구를 때만 긋는다(ADR-023).** 선은 "여기서 잘렸고
  아래로 이어진다"는 뜻이다. 이어질 것이 없는데 그으면 단추 하나를 위해 창을
  가로지르는 선이 그 단추보다 커진다. 창마다 손으로 정하지 않고 `Dialog` 가 재서
  정한다 — 다만 `ResizeObserver` 는 **그림이 그려지는 박자에 실려 오므로** 화면이
  그려지지 않는 동안에는 오지 않는다. `resize` 도 함께 듣는 이유가 그것이다.
- **적는 칸은 상자가 아니라 아래 한 줄이다(ADR-026).** 네 변을 두르면 창 안에
  상자가 여럿 생긴다 — 읽어야 할 것은 상자가 아니라 그 안의 값이다. 누르면
  그 줄이 강조색으로 굵어지는 것이 포커스 표시이고, **거기에 상자 모양 포커스
  링을 겹쳐 그리지 않는다**(`.field-underline` 이 globals.css 에서 링을 끈다) —
  링을 두면 방금 없앤 상자가 포커스할 때마다 되살아난다.
- **줄은 테두리가 아니라 `inset` 그림자로 그린다(ADR-026).** 두 가지 이유다.
  테두리를 1px→2px 로 바꾸면 칸의 높이가 그만큼 달라져 아래가 밀린다(ADR-019).
  그리고 `focus:border-[var(--…)]` 는 **기본 색 유틸리티를 이기지 못했다**
  (실제로 겪음 — CSS 규칙은 생성되는데 적용되지 않았다). 그림자는 한 속성뿐이라
  기본과 focus 가 같은 자리를 다투고 변형이 확실히 이긴다.
- **금액은 적는 동안에도 자릿점이 찍힌다(ADR-026).** 화면의 다른 모든 금액이
  그렇게 보이는데 적는 칸만 맨 숫자면 같은 값이 적을 때와 보일 때 다른 모양을
  갖는다. 글자 수가 바뀌므로 **글자 자리(caret)를 직접 되돌려 놓아야 한다** —
  앞쪽에 있던 숫자의 개수를 세어 두었다가 그 개수만큼 지난 자리로 옮긴다.
  `Number` 를 거치지 않는다: 여기서 다루는 것은 계산할 수가 아니라 적히는 중인 글자다.
- **빈 칸에 예시 값을 적어 두지 않는다(ADR-026).** 회색 예시 숫자는 값이 들어
  있는 것처럼 보인다. 이름표가 '지출 금액'이라고 이미 말한다.
- **포커스 표시를 끄는 것과 규칙에서 빼는 것은 다른 일이다.** globals.css 의
  포커스 규칙에서 `dialog` 를 빼기만 했더니 이번에는 **브라우저 기본 링**이 나와
  창을 통째로 두르는 진한 테두리로 보였다(실제로 겪음). `dialog:focus-visible`
  에 `outline: none` 을 따로 적어야 한다.
- **밑줄 칸의 포커스에서 `border-radius` 도 지운다.** 포커스 규칙이 곡선까지
  주는데, 밑줄은 `inset` 그림자라 **곡선을 따라 양 끝이 말려 올라간다**
  (실제로 겪음 — 금액·내용 칸을 누르면 줄 양쪽 끝이 둥글게 휘었다).
- **`<dialog>` 가 열릴 때 창 자신에게 포커스를 준다(Dialog.tsx).** `showModal()` 은
  창 안의 첫 번째 누를 수 있는 것에 포커스를 주는데, 그것이 대개 오른쪽 위 닫기(X)라
  기록을 저장하고 창이 다시 열리면 **방금 한 일과 상관없는 곳에 포커스 링이 남는다**
  (실제로 겪음). 그리고 globals.css 의 포커스 규칙은 **레이어 밖이라 Tailwind
  유틸리티보다 세다** — 컴포넌트에 `focus:outline-none` 을 붙여도 이기지 못하므로
  그 규칙 자체에서 `dialog` 를 뺐다.
- **네이티브 `<select>` 를 쓰지 않는다(ADR-025).** 닫힌 칸은 우리 곡선을 따르는데
  **펼친 목록은 운영체제가 그린다** — 모서리가 각지고 글자도 색도 우리 것이 아니다.
  한 동작 안에서 모양이 두 번 바뀐다. `ui/Select.tsx` 를 쓴다. 목록은 `position: fixed`
  다 — 창 본문이 `overflow-y-auto` 라 absolute 로 두면 잘린다.
- **기록 줄을 누르는 것은 고치려는 것이다(ADR-024).** 읽기 전용 '거래 상세'를 한 겹
  더 두지 않는다 — 그 화면이 보여 주던 분류·내용·금액은 목록 줄이 이미 보여 준 것과
  같았고, 누름 한 번을 값 없이 더 받았다. 그리고 고치는 창은 **새로 적는 창과 같은
  창**이다(`RecordDialog`). 같은 일을 하는 곳이 두 모양을 가지면 둘을 각각 익혀야 한다.
- **날짜를 눌러 들어온 창에 날짜 칸을 두지 않는다.** 창의 이름이 이미 그 날짜다.
  **고치는 창에는 방향 바도 두지 않는다(ADR-024)** — 지출인지 수입인지는 그 기록을
  적을 때 이미 정한 것이고, 고칠 때마다 다시 고르게 하는 것은 묻지 않아도 될 것을
  묻는 일이다. 빼되 감추지는 않는다: 금액 이름표가 '지출 금액'·'수입 금액'으로 말한다.
  같은 이유로 날짜 상세의 부제에 'N건'을 적지 않는다 — 목록이 바로 아래에 있고
  세는 일은 눈이 한다. 그 자리에는 공휴일 이름처럼 목록이 말하지 못하는 것을 둔다.
- **`--hairline` 은 `--surface-2` 위에서 보이지 않는다.** 옅은 면 위의 구분선은
  `--line` 을 쓴다(실제로 겪음 — 날짜 상세의 세 칸을 나누는 실선이 보이지 않았다).
- **활성 본문은 흰 표면에서 4.5:1 이상이어야 한다(ADR-020).** 토큰을 바꾸면
  브라우저에서 실제 대비를 다시 재고 넘긴다. '세련되게 옅은 것'과 '읽히지 않는 것'은 다르다.
- **금액을 말줄임하지 않는다(ADR-020).** 잘라서 정렬 문제를 숨기지 않는다.
  숫자와 '원'은 한 줄로 붙어 다닌다.
  뜻 없는 색을 더하면 정작 사람이 찾는 금액이 늦게 읽힌다(실제로 겪음 —
  방향색·태그 10색·요일색·강조색·틴트 배경이 한 화면에서 겹쳤다).
- **`<dialog>` 를 코드로 닫을 때의 `close` 이벤트를 사용자 동작으로 취급하지 않는다.**
  `el.close()` 가 내는 이벤트를 그대로 `onClose` 로 넘기면 부모가 이미 내린 결정을
  뒤집는다 — 날짜 상세의 '+' 가 상세를 닫자 그 close 가 상세를 통째로 언마운트해
  아무 일도 일어나지 않았다(실제로 겪음). 표시를 두어 구분하되, `close` 이벤트는
  **비동기로** 오므로 `close()` 직후에 표시를 지우면 안 된다.
- **닫힌 `<dialog>` 에 `display` 를 주지 않는다.** 브라우저가 `display:none` 으로
  숨기는 것을 덮어써서 닫힌 창이 화면에 남는다(실제로 겪음). `hidden open:grid` 를 쓴다.
- **통계의 기간은 '종류'와 '위치' 둘이다(ADR-030).** 종류는 주간·월간·연간,
  위치는 ‹ › 로 옮긴다. '이번 주·이번 달·올해'로만 두면 **되짚어 보는 화면인데
  지금밖에 볼 수 없다**(실제로 그랬다). 주간은 `2026년 9월 1주차 (08/31 ~ 09/06)`
  처럼 **날짜 범위를 함께** 적는다 — 1일이 든 주를 1주차로 세므로 이레 중 엿새가
  지난달인 주가 생긴다.
- **수입이 먼저, 지출이 가운데, 합계가 끝이다.** 들어온 것을 보고 나간 것을 보는
  차례이며, **달력 칸과 날짜 상세가 같은 차례**를 쓴다 — 같은 하루를 두 곳에서
  다른 순서로 보여 주면 눈이 매번 다시 찾는다. 합계는 앞의 둘에서 나오는 값이라
  마지막이다. 접근성 이름의 차례도 같게 둔다 — 눈으로 읽는 순서와 귀로 듣는
  순서가 다르면 같은 칸을 두 가지로 기억하게 된다.
- **숫자는 오른쪽, 글자는 왼쪽으로 맞춘다(ADR-019).** 세로로 늘어선 금액은 자릿수가
  맞아떨어져야 크기를 눈으로 비교할 수 있다. `w-28 text-right` + `.tabular`.
- **길이가 변하거나 조건부로 나타나는 것은 자리를 미리 잡는다(ADR-019).**
  있던 자리를 없애는 것도 없던 자리를 만드는 것만큼 화면을 흔든다.
- **되돌리기를 지운 줄 자리에 두지 않는다(ADR-019).** 서버가 목록을 다시 내려보내면
  그 줄이 사라지면서 버튼도 함께 없어진다 — `FR-ENTRY-11` 을 이행할 길이 사라졌던
  적이 있다(실제로 겪음). 목록 **밖**의 한 줄에 둔다.
- **목록의 줄마다 동작 버튼을 달지 않는다(ADR-018).** 줄이 다섯이면 버튼이 열 개가
  된다. 줄 자체를 누르는 곳으로 삼고, 되돌릴 수 없는 동작은 그 안쪽에 둔다.
- **차트 색을 SVG 속성에 `var(--token)` 으로 넘기지 않는다.**
  SVG 의 `fill` 은 CSS 속성이 아니라 XML 속성이라 `var()` 를 해석하지 못한다.
  축과 범례는 나오는데 도형만 안 보이는 증상으로 나타난다(실제로 겪음).
  `Charts.tsx` 의 `useTokens()` 가 실행 시점에 실제 색으로 풀어 준다.
- **태그의 색은 목록에서의 자리로 정한다(ADR-032).** id 를 해시해 색상환의 칸을
  고르면 **떨어져 앉는 것이 보장되지 않는다** — 실제로 태그 다섯 중 셋이 초록으로
  몰렸고, 285°와 255°는 서로 1.35:1 이었다. '다르다'고 말하면서 구별이 안 되는
  것은 대놓고 겹치는 것보다 나쁘다. 자리로 정하면 12칸까지는 반드시 다르다.
- **색의 밝기를 색상별 어림값으로 되돌리지 않는다(ADR-032).** 어림값으로는 노랑이
  1.73:1, 초록이 2.12:1 로 흰 바탕에서 흐려졌다(실제로 겪음). **실제 대비를 재서**
  3:1 을 넘을 때까지 어둡게 한다 — 지금 그 대상은 면이 아니라 **테두리**다(ADR-036).
  계열색(`--chart-1..6`)은 한 색의 채도 차이라 파이에 쓰지 않는다 — 그것은
  '같은 것의 정도 차이'를 뜻한다.
- **태그 색은 면과 테두리 한 쌍이다(ADR-036).** 면은 파스텔(밝기 0.82), 테두리는
  **같은 색상**을 3:1 까지 어둡게 한 색. 둘은 늘 같이 다닌다(`TagPaint`).
- **테두리는 범례 동그라미에만 두르고 파이 조각에는 두르지 않는다(ADR-037).**
  파스텔 면 위에서는 그 선만 진해 **선이 면보다 먼저 읽혔다**(실제로 겪음).
  옅게 하면 3:1 을 맡기려던 이유가 사라지므로 중간이 없다 — 파이에서는 그 몫을
  포기하고 값은 아래 목록의 글자가 말한다. 동그라미는 10px 이라 테가 없으면
  흰 바탕에 녹으므로 남긴다.
- **파스텔은 채도가 아니라 밝기의 문제다(ADR-036).** 채도만 낮췄더니(0.62 → 0.44)
  색이 **탁해질** 뿐 밝아지지 않아 '눅은 색'이지 파스텔이 아니었다(실제로 겪음).
  밝기를 올리고 3:1 을 테두리로 옮기는 것이 답이다.
- **테두리는 중립 회색이 아니라 제 색상이다(ADR-036).** 열둘이 모두 같은 테를
  두르면 테두리가 정체를 말하지 못한다. 같은 색상이어야 테가 면을 한 번 더
  확인해 준다. 그리고 **옆면을 테두리보다 진하게 만들지 않는다** — 그러면 테가
  면에 묻혀 3:1 을 테두리에 맡긴 것이 헛일이 된다(실제로 겪음 — hue 30°에서
  잘린 면 5.86 : 테두리 4.19). TC-VIEW-47 이 이 순서를 지킨다.
- **파이 조각에 테두리를 두지 않는다(ADR-032).** 흰 선을 끼우면 원이 조각조각으로
  흩어져 보인다. 나뉘는 자리는 색이 바뀌는 것으로 충분하다. 3D 파이에서 조각이
  벌어져 있는 것은 테두리가 아니라 **기하**다 — 그 틈에 보이는 것은 흰 선이
  아니라 잘린 면이고, 그것이 두께를 말한다(ADR-035). 기각된 것은 **흰** 선이다 —
  제 색상의 테두리는 반대로 조각을 묶는다(ADR-036).
- **입체감은 명암이 아니라 기하가 만든다(ADR-035).** 평면 원에 명암만 입히면
  '입체'가 아니라 '색이 어두워진 원'이다(실제로 겪음 — ADR-034 가 그것이었다).
  윗면을 타원으로 누르고 조각마다 **옆면 셋**(둘레벽 · 잘린 두 면)을 세운다.
  조각은 늘 조금 벌어져 있어야 한다 — 맞닿아 있으면 잘린 면이 보이지 않아
  두께가 둘레에서만 읽힌다.
- **기울여 본 원은 뒤에서 앞으로 그린다(ADR-035).** SVG 에는 z 축이 없고 나중에
  그린 것이 위에 온다. 차례가 틀리면 뒤 조각의 옆면이 앞 조각 위로 삐져나와
  도형이 깨진다. **recharts 로는 할 수 없다** — 조각을 데이터 차례로 그리고
  그 차례를 바꿀 길을 주지 않는다. 그래서 파이만 직접 그린다.
- **안 보이는 면을 그리지 않는다(ADR-035).** 둘레벽은 앞쪽 반(`sin θ < 0`)만,
  잘린 면은 그 면이 보는 이를 향할 때만 보인다(시작 모서리는 `cos θ < 0`,
  끝 모서리는 `cos θ > 0`). 이 판정은 눈으로 검산할 수 없다 — 틀리면
  "왜인지 이상한 도형"으로만 보인다. `ui/pieDepth.ts` 에 모아 두고 TC-VIEW-46
  이 값으로 못 박는다. **SVG 의 y 는 아래로 자라므로 투영에서 부호를 뒤집는다** —
  놓치면 원이 위아래로 뒤집힌다.
- **세 면의 밝기는 어두워지는 쪽으로만 다르다(ADR-035).** 빛은 위에서 오므로
  윗면이 가장 밝고 잘린 면이 가장 어둡다. 옆면을 **밝히면** 태그 색이 흰 바탕에서
  3:1 이 되는 경계의 값이라(ADR-032) 그 선을 넘는다(TC-VIEW-47). 밝기가 같으면
  두께가 사라진다.
- **3D 파이는 앞쪽 조각을 커 보이게 한다 — 알고 쓴다(ADR-035).** 옆면이 앞쪽에서
  더 넓게 보이기 때문이고, 차트 문헌이 3D 파이를 반대하는 이유가 이것이다.
  막는 것은 ADR-031 이 이미 둔 **목록**이다 — 이름·비중·금액이 글자로 적혀 있어
  크기를 눈으로 어림할 필요가 없다. 그 목록을 없애면 이 결정의 근거가 사라진다.
  평면으로 되돌리려면 기하를 고칠 것 없이 `TILT` 를 1 에 가깝게 두면 된다.
- **파이의 말풍선은 포인터의 왼쪽이다(ADR-033 → ADR-035).** 오른쪽에 두면 같은
  판 오른쪽 칸의 기록 목록을 덮는다(실제로 겪음). 직접 그리므로 기준점이
  **포인터 자신**이다. 왼쪽에 자리가 있는지는 **말풍선의 너비를 재서** 본다 —
  어림값으로 두었더니 자리가 남는데도 오른쪽으로 넘어갔다(실제로 겪음 —
  137px 짜리를 190px 로 봤다). 자리가 모자랄 때만 오른쪽으로 넘긴다.
- **고른 태그의 합계는 왼쪽 범례와 오른쪽 기록 머리 **양쪽**에 적는다(ADR-034).**
  기록을 읽다가 "그래서 다 해서 얼마였지"를 물었을 때 눈이 화면을 가로질러
  왼쪽으로 돌아가야 했다(실제로 겪음). 값이 겹치는 것은 비용이지만 왕복이 더
  비싸다. 둘은 `CategoryAmount.amount` 한 곳에서 온다. '합계'라는 낱말 대신
  **선**을 그어 기록과 나눈다 — ADR-031 ③ 을 지키면서 같은 일을 한다.
- **줄마다 같은 뜻의 숫자는 목록 전체가 함께 쓰는 칸에 넣는다(ADR-033).**
  줄마다 제 내용만큼만 자리를 쓰면 금액이 긴 줄에서 비중이 왼쪽으로 밀려
  **같은 종류의 숫자가 줄마다 다른 자리에 선다**(실제로 겪음 — 태그별 지출 범례).
  이름 옆에 붙이는 것도 안 된다: 이번에는 이름 길이가 자리를 정한다. 고정 폭은
  큰 금액을 잘라야 해서 ADR-020 과 부딪힌다. CSS `subgrid` 로 <ul> 의 칸을
  줄과 버튼에 물려주면 칸 너비를 **가장 넓은 줄**이 정하므로, 잘리지 않으면서
  세로로 한 자리에 선다.
- **태그별 지출은 파이다. 다만 파이만 두지 않는다(ADR-031).** ADR-020 이 도넛을
  기각했던 이유(**작은 지출이 0% 로 사라지고 범례와 금액이 멀어진다**)는 지금도
  옳다. 그래서 파이 아래에 이름·비중·금액을 글자로 적은 목록을 함께 두고,
  0 보다 큰데 1% 미만이면 '1% 미만'이라고 적는다. **그 목록은 고르는 곳이기도
  하다** — 조각에 마우스를 올리는 일은 자판으로 할 수 없으므로 같은 일을 하는
  버튼이 반드시 있어야 한다. 색은 **차트 계열색**이다 — 거래 방향의 빨강을
  여기서 되풀이하지 않는다.
- **수입과 지출은 같은 눈금에 그린다(ADR-020).** 축을 나누면 비슷한 높이가 비슷한
  금액처럼 보인다. 정확한 값을 읽는 표는 **화면에서는 뺐지만 지우지는 않았다** —
  `sr-only` 로 남아 있다(ADR-037). 마우스를 쓸 수 없는 사람이 값에 닿는 유일한
  길이므로 그 표를 지우면 "hover 로만 값을 보게 하지 않는다"가 깨진다.
- **가리킨 자리를 칠하지 않는다(ADR-037).** 막대 차트에서 가리킨 기간의 칸 전체가
  연보라로 칠해졌었다. 띠가 막대보다 넓은 데다 보라는 이 화면에서 '지금 있는 곳'과
  주 동작의 색이다(ADR-017). 색을 바꿔도 마찬가지다 — 따라다녀야 하는 것은
  값이지 자리가 아니다. recharts 는 `cursor={false}`.
- **recharts 의 `formatter` 가 받는 `name` 은 dataKey 가 아니라 `<Bar name>` 이다.**
  `name === 'expense'` 로 견주던 때에는 그 견줌이 늘 거짓이라 **지출까지 '수입'으로**
  적혔다(실제로 겪음). 이름을 그대로 쓰면 된다.
- **recharts 막대의 등장 애니메이션을 켜 두지 않는다.** `requestAnimationFrame` 을
  타는데 그림이 그려지지 않는 동안에는 그 박자가 오지 않아 막대가 **높이 0 인 첫
  프레임에 멈춘다** — 축과 눈금은 나오는데 막대만 없는 증상이다(실제로 겪음).
  `isAnimationActive={false}`.
- **내역도 프롬프트 하나로 찾는다(ADR-040).** 기록을 **적는** 길이 한 줄인데
  **찾는** 길만 칸 일곱 개인 것은 같은 제품의 두 얼굴이다. `SearchDock` 은
  `PromptDock` 과 같은 실루엣을 쓰되 **첨부가 없다** — 찾는 데에는 영수증이
  필요 없고, 자리만 차지하는 단추는 그 화면에서 할 수 없는 일을 할 수 있는
  것처럼 보이게 한다.
- **조회 문장의 해석도 해석 경계 안에서 한다(ADR-040).** 경계 밖에 두면 나가는
  지점이 둘이 되어 §2 불변조건 1 과 `FR-ENTRY-15` 의 판정 근거가 무너진다.
  `InterpretProvider` 에 `interpretQuery` 를 더했고, 기기 안 규칙과 외부 수단이
  **같은 계약**을 돌려준다 — 그래야 외부가 죽어도 이어받는 길이 살아 있다.
- **대화는 두 순간에 자리를 옮긴다(ADR-041).** 물으면 **그 물음으로** 내려가고
  (`scrollIntoView({block:'start'})`), 답이 오면 **답의 끝이 화면의 끝**이 된다.
  끝으로 갈 때 `scrollIntoView` 를 쓰면 안 된다 — 뷰포트 바닥에 맞추는데 그 바닥은
  프롬프트 바가 덮고 있어 마지막 줄이 가려진다. `.has-dock` 이 바의 높이만큼
  아래 여백을 이미 잡아 두었으므로 **문서의 끝**(`window.scrollTo({top: scrollHeight})`)
  으로 내리면 그 여백이 바의 자리가 된다. `.has-dock` 의 `scroll-padding-bottom` 은
  소용이 없다 — 실제로 구르는 것은 그 칸이 아니라 **문서**다.
- **`behavior: 'smooth'` 를 믿지 않는다.** 미끄러지는 것은 그림이 그려지는 박자에
  실려 오므로 화면이 그려지지 않는 동안에는 **한 걸음도 나아가지 않는다**(실제로
  겪음 — 문서가 880px 남았는데 스크롤 위치가 0 그대로였다). `ResizeObserver` 가
  안 오는 것도, recharts 막대가 높이 0 에 멈추는 것도 **같은 원인**이다. 움직임이
  꼭 필요한 것이 아니면 바로 뛴다.
- **저장소에 담는 모양을 바꾸면 열쇠에 번호를 올린다.** 열쇠가 그대로면 지난
  모양으로 담긴 것이 새 화면으로 복원되어 터진다 — 실제로 겪음
  (`Cannot read properties of undefined (reading 'map')`: 답이 `items` 하나였던
  시절의 턴에는 `groups` 가 없다). `hanjul.search.turns` → `...turns.v2`.
  번호를 올리는 것을 **잊을 것까지 계산해** 읽을 때 모양을 확인하고 맞는 것만
  살린다(`SearchChat` 의 `sane()`) — 저장소의 값은 우리가 쓴 것이지만 **언제**
  쓴 것인지는 알 수 없다.
- **한 문장이 조회를 여럿 부를 수 있다(ADR-042).** "지출과 수입 따로 보여줘"는
  한 번 묻고 **두 번 조회**하는 일이다. 합쳐서 한 목록으로 내놓으면 사용자가 말한
  '따로'를 화면이 되돌린다. 그래서 해석의 반환값이 조건 하나가 아니라
  **몫의 배열**(`QueryPart[]`)이다 — 무엇으로 나누든 같은 모양이라 나중에
  태그별·기간별로 나눠도 표시를 새로 만들지 않는다.
- **'따로'가 없어도 수입과 지출을 둘 다 말하면 나눈다(ADR-042).** 그러지 않으면
  먼저 걸리는 한쪽만 조건이 되어 **사용자가 말한 절반이 조용히 사라진다.**
  그리고 나눌 때 방향 낱말을 조건으로 쓰지 않더라도 **문장에서는 덜어 낸다** —
  덜어 내지 않으면 '지출과 수입'이 통째로 내용 검색어가 되어 두 몫이 다 0 건이
  된다(실제로 겪음).
- **외부 수단이 잠깐 막힌 것이면 다시 물어본다(ADR-043).** 429·5xx 는 우리가
  잘못한 것이 아니라 그쪽이 바쁜 것이다. 한 번도 다시 묻지 않으면 그때마다 규칙
  기반으로 떨어져 사용자는 **자유롭게 적은 문장이 통하지 않는다**고 느낀다
  (실제로 겪음 — 503 이 이어지는 동안 줄곧 규칙만 돌았다). 두 번까지, 0.7초씩
  늘리며. 다른 모델로 갈아타지 않는다 — 모델마다 성질이 달라 **조용히 다른 답**이
  된다. 되풀이는 `gemini.ts` 의 `askGemini()` 한 곳에 둔다(나가는 자리를 늘리지
  않는다). 모델을 바꾸려면 `GEMINI_MODEL` 환경 변수를 쓴다.
- **규칙 기반은 남은 말을 통째로 검색어로 삼지 않는다(ADR-043).** 그러면
  "이번주에 학식먹었어? 먹었다면 얼마썼어?" 가 `내용 "학식먹었어 먹었면 어"` 가
  되어 **반드시 0 건**이다 — 있는 것을 못 찾은 것이 아니라 **찾을 수 없는 것을
  만들어 낸 것**이다. 낱말마다 풀이말의 꼬리를 떼고 **하나만 남을 때** 그것을 쓴다.
  여럿이면 **검색어를 두지 않는다** — 규칙이 가릴 수 없으면 모르는 채로 두고
  기간·방향으로 찾아 주는 편이 0 건보다 낫다. 말을 다 알아듣는 일의 본체는
  외부 수단이고, 여기는 그것이 죽었을 때의 길이다.
- **조회 프롬프트에 표의 생김새와 말 옮김 규칙을 함께 싣는다(ADR-041).**
  "조건을 뽑아라"라고만 했더니 '이번달 사용 내역'의 **'사용'이 내용 검색어로 새어
  0 건**이 나왔다(실제로 겪음). 무엇을 어디서 찾는지 모르면 남는 말을 전부
  검색어로 밀어 넣는다. 셋을 준다: ① `records` 의 칸과 그 칸에 무엇이 들어 있는지
  ② 같은 뜻으로 볼 말(사용·소비·쓴 = 지출) ③ **조건이 아닌 말**(내역·목록·보여줘).
  ③ 이 빠지면 꼬리말이 검색어가 된다. 기기 안 규칙(`queryRules.ts`)의
  `FILLER`·방향 규칙도 같은 말을 알아야 한다 — 폴백이 더 못 알아들으면 안 된다.
- **조회 해석은 조건과 '알아들은 조건의 목록'을 함께 돌려준다(ADR-040).**
  조건만 돌려주면 **알아듣지 못해 비어 있는 것**과 **원래 그 조건이 없는 것**이
  값에서 구별되지 않는다. 그러면 사용자도 '못 찾음'과 '잘못 알아들음'을 가릴 수
  없다. 목록이 비면 화면을 **옮기지 않는다** — 조건 없는 전체 목록이 뜨면
  사용자는 자기 문장이 통했다고 읽는다.
- **내역은 대화다(ADR-041).** 사용자의 말은 오른쪽 말풍선(흰 바탕 + 강조색
  테두리), 답은 왼쪽 말풍선. 첫 화면은 **빈 바탕**이다 — 점선 상자도 안내 문구도
  두지 않는다. 무엇을 하라는 말은 프롬프트의 자리 표시가 이미 하고 있다.
- **무엇으로 찾았는지를 상시로 적지 않는다(ADR-041).** '· 지출만'·'적으신 말: …'은
  **바로 위 말풍선이 이미 한 말**이라 ADR-031 이 금한 사족이다(실제로 붙였다가
  지적받았다). **0 건일 때만** 적는다 — 그때만 '못 찾음'과 '잘못 알아들음'이
  갈리고, 어떻게 알아들었는지를 모르면 다시 적어 볼 수도 없다.
- **보낸 말이 답보다 먼저 선다(ADR-041).** 답을 기다렸다가 말과 답을 한꺼번에
  붙이면 보낸 직후 잠깐 동안 화면이 **내가 무엇을 물었는지 말하지 않는다** —
  대화에서 그것은 말을 삼킨 것이다. 말이 먼저 서면 답이 올 자리도 함께 잡혀
  화면이 흔들리지 않는다(ADR-019). 기다리는 표시는 점 셋과 한 마디면 된다.
- **답 말풍선은 판의 폭을 다 쓴다(ADR-041).** 다음 물음은 아래에 오므로 자리를
  다툴 것이 없다. 사용자의 말풍선만 좁게 두어 누가 한 말인지 폭으로도 갈린다.
- **조회 문장의 대화는 주소에 싣지 않는다(ADR-041 — ADR-040 ④ 철회).** 흐름을
  주소 한 줄에 담을 수 없다. 대신 `sessionStorage` 에 둔다 — 결과를 눌러 달력에
  다녀왔을 때 대화가 통째로 사라지면 안 되기 때문이다. **링크로 결과를 건네줄 수
  없게 된 것**이 이 결정의 값이다.
- **같은 화면에서 조건만 바꾸는 이동에 `scroll={false}` 를 준다(ADR-038).**
  Next 의 `<Link>` 는 기본이 '맨 위로'다. 다른 화면으로 갈 때는 맞지만 같은
  화면에서 조건만 바꿀 때는 **읽던 자리를 빼앗는다** — 통계에서 3개월/6개월을
  누르면 화면이 통째로 위로 올라갔다(실제로 겪음). `router.push` 는 어디로 가든
  `scroll` 을 **분명히 적는다**: 빠뜨린 것과 일부러 맨 위로 보내는 것을 구별할
  수 있어야 한다.
- **네이티브 `<form method="get">` 을 쓰지 않는다(ADR-038).** 브라우저가 **문서를
  통째로 다시 받는다** — 화면이 하얘졌다가 처음부터 그려지고, 스크롤은 맨 위로
  가고, 클라이언트에 남아 있던 것이 사라진다. 바뀌는 것은 목록 한 덩어리인데
  값은 화면 전체다. `ui/QueryForm` 이 전송만 가로채고 `method`·`action` 은
  그대로 두어 자바스크립트가 없을 때의 길을 남긴다.
- **문서 제목을 `metadata` 에 두지 않는다(ADR-039).** Next 는 화면마다 metadata 를
  따로 흘려보낸다. 그래서 같은 화면에서 조건만 바꿔도 `<title>` 이 지워졌다 다시
  꽂히고, 그 사이 문서에 제목이 없어 **브라우저 탭이 주소를 보여 준다**(실제로
  겪음 — 60ms 남짓). 레이아웃은 같은 라우트 안에서 다시 그려지지 않으므로
  제목을 레이아웃의 JSX 로 둔다. React 19 가 head 로 끌어올린다.
  · 이 증상이 눈에 띈 것은 **recharts 가 SVG 안에 비어 있는 `<title>` 을 그려 두기**
  때문이다 — head 의 제목이 사라진 순간 그 빈 제목이 문서의 제목이 된다.
- **차트를 눌러도 초점을 받지 않게 한다(ADR-039).** recharts 는 자판으로 값을
  훑으라고 SVG 에 `tabindex` 와 `role="application"` 을 준다. 그 role 때문에
  브라우저가 **마우스 클릭까지** `:focus-visible` 로 쳐서 차트 둘레에 링을 그린다
  (실제로 겪음). `accessibilityLayer` 를 끄면 링과 함께 **자판으로 값을 읽을 길이
  사라진다** — 표를 화면에서 내린 뒤(ADR-037) 그 길은 더 귀하다. 감싼 칸의
  `mousedown` 기본 동작만 막으면 **초점만** 안 가고 Tab 으로 오는 길은 그대로다.
- **이 규칙들은 `test/view.navscroll.test.ts` 가 소스를 훑어 검사한다.** 화면을 만들
  때마다 새로 지켜야 하는 규칙이고, 어기면 **화면이 조용히 튀기만 할 뿐 아무 것도
  실패하지 않는다.** 검사기를 처음 만들었을 때 `href={spanHref(...)}` 처럼 주소를
  계산해 만든 링크 셋이 그냥 지나쳤다 — 정적으로 알 수 없으면 말하게 해야 한다.
- **`I18nProvider` 는 클라이언트 경계 안에 둔다.** 컨텍스트를 쓰므로 서버 컴포넌트에서
  import 하면 전체가 500 이 된다(실제로 겪음). `src/app/providers.tsx` 참조.
- **부모가 넘긴 배열을 `useEffect` 로 state 에 복사하지 않는다.** 배열은 매 렌더
  새 참조라 의존성이 매번 바뀌어 렌더가 무한히 반복된다. 화면이 "렌더 미완료"로
  멈추는 증상으로 나타난다(실제로 겪음). 처리한 것은 **id 집합**으로 기억한다 —
  `CandidateReview` 참조.
- **달력 칸에 `<button>` 을 쓸 때 `flex flex-col` 을 준다.** 브라우저는 버튼의 내용을
  버튼이 내용보다 클 때 **세로 가운데로 민다.** `text-left` 만으로는 가로만 잡히고,
  날짜 숫자가 칸 한복판에 떠서 달력으로 읽히지 않는다(실제로 겪음).
- **탭 밑줄을 `-bottom-px` 로 컨테이너 밖에 걸치지 않는다.** 넘친 1px 때문에
  `overflow-x-auto` 가 세로 스크롤바까지 만들어 탭 줄 오른쪽에 15px 짜리 회색 띠가
  생긴다(실제로 겪음, `scrollHeight 41 > clientHeight 40` 으로 확인). `bottom-0` 을 쓴다.
- **네이티브 `<dialog>` 에 `m-auto` 를 명시한다.** 리셋이 margin 을 0 으로 만들어
  두면 팝업이 좌상단에 붙는다. `backdrop:bg-transparent` 를 주면 전역 backdrop 이
  덮여 배경이 흐려지지 않는다(둘 다 실제로 겪음).
- **다건 입력의 방향은 조각별로 판정한다.** 문장 전체를 보면 뒤쪽의 "받았어"가
  앞의 지출까지 수입으로 만든다(실제로 겪음, TC-ENTRY-46).
- **개발 서버가 도는 중에 `.next` 를 지우지 않는다.** Turbopack 캐시가 깨져
  서버가 패닉으로 죽는다. 서버를 먼저 멈춘다(실제로 겪음).
- **응답 스키마의 `enum` 에 빈 문자열을 넣지 않는다.** `enum: ['income','expense','']`
  는 `HTTP 400 enum[2]: cannot be empty` 로 거부된다(실제로 겪음). '모름'은 빈 값이
  아니라 **required 에서 빼서 항목을 생략**하는 것으로 표현한다.
- **모델은 둘이다 — `gemini-3.1-flash-lite` 를 먼저, `gemini-3.6-flash` 를 그다음
  (ADR-044).** 먼저 부르는 것이 가벼운 쪽인 이유는 이 제품이 시키는 일(한 줄을
  구조로 바꾸기·조회 조건 뽑기)이 긴 추론을 필요로 하지 않기 때문이다.
  대체 모델을 두는 이유는 **모델마다 한도와 과부하가 따로 오기** 때문이다 —
  한쪽이 막혀도 다른 쪽은 멀쩡한 경우가 잦다. 같은 모델을 다시 부르는 것
  (ADR-043)과 **다른 모델을 부르는 것은 다른 약**이다: 앞은 잠깐 막힌 것에,
  뒤는 그 모델이 한동안 바쁜 것에 듣는다. 400·403·404 는 다시 물어도 같으므로
  그 모델은 그 자리에서 포기하고 다음으로 넘어간다. 갈아탄 사실은 **서버 로그에
  남긴다** — 조용히 갈아타면 왜 답이 달라졌는지 알 수 없다.
  바꾸려면 `GEMINI_MODEL`·`GEMINI_MODEL_FALLBACK` 환경 변수를 쓴다.
- **`gemini-2.5-flash` 를 쓰지 않는다.** 모델 목록 조회에는 나오지만 **새로 발급한
  키로 호출하면 404** 다("no longer available to new users").
- **외부 호출 실패를 조용히 삼키지 않는다.** 전에는 `catch` 가 사유를 버려서
  폴백은 됐지만 원인을 아무 데서도 알 수 없었다. `gemini.ts` 의 `fail()` 이
  서버 로그에 남기고 `failureDetail` 로 화면까지 올린다(실제로 겪음).
- **`better-sqlite3` 를 쓰지 않는다.** Windows 에서 네이티브 빌드가 필요하다.
  Node 24 의 `node:sqlite` 로 충분하다.
- **기본 분류는 "분류가 하나도 없을 때만" 넣는다.** 사용자가 전부 지운 상태를 되돌리면
  `FR-CAT-03` 이 무의미해진다.

## 8. 보안 규칙

- `data/` 와 `.env*` 는 커밋하지 않는다. 사용자의 가계 기록과 API 키가 들어간다.
- `GEMINI_API_KEY` 는 서버에서만 읽는다. 클라이언트 번들에 넣지 않는다.
- 외부로 나가는 것을 늘리려면 먼저 `docs/` 의 `FR-ENTRY-15`·`FR-ENTRY-16` 을 고친다.
  코드부터 고치면 사용자에게 보여 주는 "나가는 항목" 목록과 실제가 어긋난다.
  **실제로 이 순서로 했다** — 내역 검색(ADR-040)이 검색어를 밖으로 보내게 되었을 때
  RFP→PRD→SRS 를 먼저 고치고 `geminiProvider.outboundFields` 의 문구를 바꾼 뒤에
  코드를 썼다. `TC-ENTRY-40` 이 그 문구가 두 길을 모두 말하는지 값으로 본다.
- **나가는 길은 둘이다 — 기록 입력과 내역 검색.** 둘 다 `gemini.ts` 한 파일 안에
  머문다. 파일을 하나 더 만들어 거기서 부르면 `test/boundary.test.ts` 가 잡는다.

## 9. 작업 단위를 끝내는 절차 (건너뛰지 않는다)

> **이 절은 참고가 아니라 순서다.** 아래 5단계를 마치기 전에는 어떤 작업도
> "끝났다"고 말하지 않는다. 실제로 이 순서를 어겨 본 적이 있다 —
> 코드를 끝내고 완료 보고를 한 뒤에야 ADR 을 채웠고, 그동안 문서는 코드가 이미
> 버린 결정(ADR-003 의 "규칙 기반 기각")을 사실처럼 말하고 있었다.

### 순서

1. **코드를 쓴다.**
2. **TC 를 쓴다.** 새 동작이면 `docs/tc/TC_*.md` 에 TC 를 **먼저** 정의하고,
   테스트 이름에 `[TC-<COMP>-NN]` 을 태깅한다. TC 없이 테스트를 늘리지 않는다.
3. **검증한다.** `npm run verify` — 타입·시험·TC 대조·문서 드리프트를 한 번에 본다.
4. **문서를 역반영한다.** 아래 표대로. 영향이 닿는 **가장 상위 문서부터** 내려온다
   (요구가 새로 생겼으면 RFP 부터, 보장 수준만 달라졌으면 SRS 부터).
   고친 문서는 **버전을 올리고 변경 이력에 한 줄 남긴다.**
   하위 문서의 `기준 문서` 버전 표기도 같이 올린다 — 이것이 가장 자주 빠진다.
5. **다시 `npm run verify`.** 통과해야 끝이다. 그다음에 완료를 말한다.

### 층마다 문장의 주어가 다르다 (되돌리지 않는다)

같은 요구가 층을 지나며 **언어를 바꾼다.** 층이 언어를 바꾸지 않으면 그 층은
윗층의 초벌이 되어 존재할 이유가 없어진다.

| 문서 | 주어와 문형 | 그 층이 더하는 것 |
|---|---|---|
| MRD | 사람 — "사용자는 ~한 상황에서 ~한 문제를 겪는다" | 문제와 그 근거 |
| RFP | **사용자 또는 제품** — "사용자는 ~할 수 있어야 한다" · "~은 ~되어야 한다" | 요구 번호의 탄생, 우선순위, 범위·비범위 |
| PRD | 사용자의 행동 — "**Given** ~ **When** ~ **Then** ~" | 여정과 관찰 가능한 수용 조건 |
| SRS | **시스템** — "시스템은 ~해야 한다" | 판정할 수 있는 조건 · 검증 유형 · 수치 합격선 |
| SDD | 구조 — "~를 ~로 둔다" | 그 선택의 이유와 되돌릴 조건 |
| TC | 판정 — "~이면 Pass" | 절차와 증거 |

**RFP 에 "시스템은" 을 쓰지 않는다.** 실제로 그렇게 적혀 있었다 — 요구 39개가
전부 "시스템은 ~해야 한다"였고, SRS 가 같은 번호를 같은 문형으로 다시 적어
두 층이 겹쳐 보였다(지적받음). 견본은 `missing-person-detection` 프로젝트다:
그쪽 RFP 에는 "시스템은"이 **0건**, SRS 에는 **89건**이다.

`docs/guideline/` 이 이 결정을 따라 고쳐졌다 — `RFP_guide`(문형·예제·칸 이름·
금지·체크리스트) · `README`(관통 표 + 긍정형 대조 표) · `spec_guide`(체인 표) ·
`SRS_guide`(정련 예시의 RFP 칸 + 반대 방향 체크). **앞으로 볼 가이드는 이 사본이다.**
`project-design/docs/guide/` 의 원본은 고치기 전 문장을 그대로 갖고 있으나
**deprecated 로 정해졌다** — 그쪽을 근거로 이 결정을 되돌리지 않는다.

가이드 폴더는 `.gitignore` 에 있어 이력이 남지 않는다. 고칠 일이 있으면 같은
커밋에서 이 절도 함께 손본다 — 기계가 잡아 주지 못하는 유일한 자리다.

### 무엇을 역반영하는가

| 무슨 일이 있었나 | 같이 갱신할 것 |
|---|---|
| 동작·정책이 바뀜 | 해당 `FR`/`NFR` + `docs/tc/TC_*.md` + 추적성 표 |
| 요구 문장을 손댐 | 그 층의 **주어와 문형**을 위 표에서 확인한다. 층을 건너뛴 문장은 정합 검사를 통과해도 층 하나를 지운다 |
| 없던 요구가 필요해짐 | **RFP 에 다음 빈 번호를 먼저 발급** → PRD → SRS → TC 순으로 내린다 |
| 설계 선택을 바꿈 / 새로 정함 | `docs/sdd/SDD.md` ADR 에 **행을 더한다.** 기존 행은 지우지 않고 `Superseded(→ADR-0NN)` 로 남긴다 |
| 구현하다 요구끼리 충돌을 발견 | 코드로 우회하지 말고 **문서를 먼저 고친다.** 충돌을 발견한 사실 자체를 ADR 의 선택 이유에 적는다 |
| 미결이 풀림 | 소유 문서의 미결 표를 `Decided` 로 바꾸고 **반영 위치를 연결**한다 |
| 새 API·서버 액션 | 이 파일 §5 계약 표 |
| 구현하며 겪은 함정 | 이 파일 §7 정책 로그 (요구가 아니라 컨텍스트다) |
| 수치 합격선 | **SRS §3 만 소유한다.** TC 는 인용만 한다 |

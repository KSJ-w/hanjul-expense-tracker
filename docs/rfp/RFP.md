## 1. 문서 목적과 경계

이 문서는 아래 질문에 답한다.

- 이번 개발의 범위 안에 있는 것과 밖에 있는 것은 무엇인가
- 시스템이 제공해야 하는 결과는 무엇인가 (`FR-<COMP>-NN`)
- 그 결과가 얼마나 잘 제공되어야 하는가 (`NFR-<COMP>-NN`)
- 무엇을 근거로 수용을 판정할 것인가

**이 문서는 특정 API·DB·클래스·모델·라이브러리를 규정하지 않는다.** 요구는
관찰 가능한 결과로만 적으며, 그것을 무엇으로 어떻게 만드는지는 SDD가 소유한다.
사용자 스토리와 수용 조건은 PRD가, 수치 합격선과 검증 유형은 SRS가, 시험 절차는
TC가 소유한다.

### 컴포넌트 약칭

요구를 나누는 축이며, 이후 TC 문서를 나누는 축과 같다. 한번 정한 약칭은 바꾸지
않는다.

| 약칭 | 영역 | 담당 관심사 |
|---|---|---|
| `ENTRY` | 기록 | 사용자가 그때그때 남기는 기록이 만들어지고 확정되고 고쳐지는 모든 것 — 자연어·이미지·직접 입력, 확인, 수정·삭제·되살리기, 반복 항목, 근거 이미지. **파일을 통한 일괄 반입은 `VIEW`가 소유한다**(반출과 짝이므로 한 축에 둔다) |
| `CAT` | 분류 | 사용자의 분류 체계 — 추가·변경·삭제, 기본 제공, 자동 배정의 경계, 고친 분류의 반영 |
| `VIEW` | 되짚어 보기 | 쌓인 기록을 사용자가 다시 얻는 모든 방법 — 날짜별, 기간 요약, 조건 검색, 예산 대비, 파일 반출·반입 |

## 2. 상위 문제와 방향

가계부는 시작하지 못해서가 아니라 이어가지 못해서 실패한다. 조사에서 가계부를
현재 작성하는 사람보다 과거에 작성하다 중단한 사람이 더 많았고, 쓰지 않는 이유의
첫머리는 "귀찮아서"였다(MRD §2). 병목은 분석의 정교함이 아니라 **기록 한 건을
남기는 비용**에 있다.

따라서 이번 개발은 기록의 마찰을 없애는 것을 첫 번째 목표로 하고, 자동 해석을
그 수단으로 쓰되 **자동 해석이 사람을 대신해 결정하지는 않게** 한다.

**보존해야 할 원칙** (MRD §4 계승)

1. 기록의 마찰을 가장 먼저 줄인다.
2. 자동 해석은 제안이지 확정이 아니다.
3. 자동이 실패해도 길이 끊기지 않는다.
4. 분류는 사용자의 것이다.
5. 처음 열었을 때 무엇을 하는 도구인지 알 수 있어야 한다.
6. 밖으로 나가는 것은 최소한으로 한다.
7. 기록은 사용자의 손에 남는다.

## 3. 범위와 비범위

### 3.1 범위

| 범위 | 제공해야 하는 결과 |
|---|---|
| 자연어 입력으로부터의 기록 | 사용자가 자기 말로 적은 한 줄이 날짜·금액·분류·수입/지출 구분을 갖춘 기록으로 남는다 |
| 이미지 입력으로부터의 기록 | 영수증·결제 내역 이미지가 같은 형태의 기록으로 남는다 |
| 사람의 확인 | 자동 해석의 결과는 사용자의 확인을 거쳐서만 확정된다 |
| 실패 지점에서의 이어받기 | 해석이 실패하거나 일부만 됐을 때 사람이 그 상태에서 기록을 완성한다 |
| 직접 기록과 정정 | 자동 해석 없이 기록을 만들고, 확정된 기록을 고치고 지우고 되살린다 |
| 반복 항목 | 매달 반복되는 지출·수입을 매번 다시 적지 않는다 |
| 근거 이미지 보관 | 기록의 출처가 된 이미지를 그 기록에서 다시 확인한다 |
| 사용자 분류 체계 | 사용자가 분류를 만들고 유지하며, 시작 시점부터 쓸 분류가 있다 |
| 고친 분류의 반영 | 한번 고쳐 둔 분류가 이후 같은 성격의 입력에 반영된다 |
| 날짜별 조회 | 어느 날 무엇이 있었는지를 날짜 기준으로 되짚는다 |
| 기간 요약 | 주·월·연 단위로 수입·지출의 크기와 구성을 본다 |
| 조건 검색 | 기간·분류·금액·적은 내용으로 지난 기록을 찾는다 |
| 예산 대비 | 스스로 정한 한도와 실제 지출을 견준다 |
| 파일 반출·반입 | 기록을 파일로 내보내고 다시 들여온다 |
| 외부 수단 없이도 기록 | 외부 해석 수단을 쓸 수 없어도 기록하는 일이 멈추지 않는다 |

### 3.2 비범위

**비범위는 이 문서가 소유한다.** PRD·SRS는 인용만 하고, 추가가 필요하면 여기를
먼저 고친다. (MRD §5.2 계승)

- 자연어를 통한 조회·수정·삭제·설정 변경 — 자연어는 기록을 남기는 데만 쓴다
- 금융기관 계좌·카드의 자동 연동과 거래 내역 수집 (§7의 법적 제약)
- 여러 사용자, 계정·로그인, 가족·부부 공유
- 모바일 전용 애플리케이션
- 외화 표기와 환산, 한국어 외 언어
- 투자·부동산·순자산 관리
- 계좌·결제수단별 잔액 추적
- 세무 신고용 자료 생성
- 자동 해석의 정확도를 높이기 위한 학습 모델의 자체 개발
- 기록의 외부 백업·동기화 서비스 제공

## 4. 전체 흐름

1. 사용자가 제품에 접근하면 기록을 남기는 수단이 곧바로 주어진다.
2. 사용자가 자기 말로 한 줄을 적거나 이미지를 제공한다. 자동 해석 없이 직접
   입력하는 길도 같은 자리에서 열려 있다.
3. 시스템이 입력을 해석해 날짜·금액·분류·수입/지출 구분을 채운 **기록 후보**를
   만든다. 한 번의 입력에 여러 건이 담겼으면 각각을 별개의 후보로 만든다.
4. 시스템이 기록 후보를 사용자에게 제시한다. 해석에 실패했거나 일부만 채워졌으면
   채워진 만큼을 제시한다.
5. 사용자가 후보의 항목을 확인하고, 필요하면 고친다. 이 단계를 거치지 않은 후보는
   기록이 되지 않는다.
6. 사용자가 확인하면 **확정된 기록**이 되어 사용자의 기기에 남는다. 근거가 된
   이미지가 있으면 그 기록에 붙어 함께 남는다.
7. 사용자가 확인 단계에서 분류를 고쳤다면, 그 사실이 이후 같은 성격의 입력에
   반영된다.
8. 확정된 기록은 달력으로 날짜별로, 기간 요약으로 주·월·연 단위로, 조건 검색으로
   찾아서, 예산 대비로 한도와 견주어 다시 얻을 수 있다.
9. 사용자는 언제든 기록을 파일로 반출할 수 있고, 반출한 파일로 다시 반입할 수 있다.

## 5. 기능 요구사항

### 5.1 ENTRY — 기록

| ID | 요구 | 우선순위 |
|---|---|---|
| `FR-ENTRY-01` | 시스템은 사용자가 자연어로 적은 문장으로부터 날짜·금액·분류·수입/지출 구분을 채운 기록 후보를 제시해야 한다 | M |
| `FR-ENTRY-02` | 시스템은 문장에 포함된 상대적 날짜 표현을 확정된 날짜로 해석해 기록 후보에 반영해야 한다 | M |
| `FR-ENTRY-03` | 시스템은 한 번의 입력에 둘 이상의 거래가 담긴 경우 각각을 별개의 기록 후보로 제시해야 한다 | S |
| `FR-ENTRY-04` | 시스템은 사용자가 제공한 이미지로부터 기록 후보를 제시해야 한다 | M |
| `FR-ENTRY-05` | 시스템은 사용자의 확인을 거치지 않은 기록 후보를 확정된 기록으로 저장해서는 안 된다 | M |
| `FR-ENTRY-06` | 시스템은 사용자가 확인 전에 기록 후보의 각 항목을 고칠 수 있게 해야 한다 | M |
| `FR-ENTRY-07` | 시스템은 해석에 실패했거나 일부 항목만 채워진 경우에도 사용자가 그 상태에서 기록을 완성할 수 있게 해야 한다 | M |
| `FR-ENTRY-08` | 시스템은 자동 해석을 거치지 않고 사용자가 직접 기록을 만들 수 있게 해야 한다 | M |
| `FR-ENTRY-09` | 시스템은 확정된 기록을 사용자가 고칠 수 있게 해야 한다 | M |
| `FR-ENTRY-10` | 시스템은 확정된 기록을 사용자가 지울 수 있게 해야 한다 | M |
| `FR-ENTRY-11` | 시스템은 사용자가 지운 기록을 되살릴 수 있게 해야 한다 | S |
| `FR-ENTRY-12` | 시스템은 사용자가 등록한 반복 지출·수입을 해당 시점에 기록 후보로 제시해야 한다 | S |
| `FR-ENTRY-13` | 시스템은 기록의 근거가 된 이미지를 그 기록에서 다시 확인할 수 있게 보관해야 한다 | S |
| `FR-ENTRY-14` | 시스템은 외부 해석 수단의 응답 실패가 직접 기록하는 경로를 막지 않게 해야 한다 | M |
| `FR-ENTRY-15` | 시스템은 입력의 해석과 **조회 요청의 해석** 외의 목적으로 사용자의 기록이나 이미지를 외부로 내보내서는 안 된다 | M |
| `FR-ENTRY-16` | 시스템은 해석을 위해 외부로 나가는 항목이 무엇인지 사용자가 확인할 수 있게 해야 한다 | S |
| `FR-ENTRY-17` | 시스템은 제품에 처음 접근한 사용자에게 기록을 남기는 수단을 별도의 안내 없이 제시해야 한다 | M |
| `FR-ENTRY-18` | 시스템은 사용자가 이미지를 첨부할 때 그 이미지가 외부로 전송된다는 사실과 민감한 부분을 가릴 수 있다는 안내를 제시해야 한다 | M |

### 5.2 CAT — 분류

| ID | 요구 | 우선순위 |
|---|---|---|
| `FR-CAT-01` | 시스템은 사용자가 분류를 추가할 수 있게 해야 한다 | M |
| `FR-CAT-02` | 시스템은 사용자가 분류의 이름을 바꿀 수 있게 해야 한다 | M |
| `FR-CAT-03` | 시스템은 사용자가 분류를 지울 수 있게 해야 한다 | M |
| `FR-CAT-04` | 시스템은 사용을 시작하는 시점에 바로 쓸 수 있는 분류를 미리 제공해야 한다 | M |
| `FR-CAT-05` | 시스템은 수입에 쓰는 분류를 지출에 쓰는 분류와 구분해 제공해야 한다 | S |
| `FR-CAT-06` | 시스템은 자동 해석에서 사용자가 보유하지 않은 분류를 임의로 만들어 배정해서는 안 된다 | M |
| `FR-CAT-07` | 시스템은 사용자가 확인 단계에서 분류를 고친 사실을 이후 같은 성격의 입력에 반영해야 한다 | S |
| `FR-CAT-08` | 시스템은 기록이 남아 있는 분류를 사용자의 확인 없이 지워서는 안 된다 | M |

### 5.3 VIEW — 되짚어 보기

| ID | 요구 | 우선순위 |
|---|---|---|
| `FR-VIEW-01` | 시스템은 달력 형태로 날짜별 기록의 존재를 제시해야 한다 | M |
| `FR-VIEW-02` | 시스템은 사용자가 선택한 날짜의 기록 목록을 제시해야 한다 | M |
| `FR-VIEW-03` | 시스템은 주·월·연 단위 기간의 수입·지출 합계를 제시해야 한다 | M |
| `FR-VIEW-04` | 시스템은 기간의 지출을 분류별 구성으로 제시해야 한다 | M |
| `FR-VIEW-05` | 시스템은 기간의 수입·지출 변화를 시간 축에 따라 제시해야 한다 | S |
| `FR-VIEW-06` | 시스템은 기간·분류·금액·적은 내용을 조건으로 기록을 찾을 수 있게 해야 한다 | S |
| `FR-VIEW-07` | 시스템은 조건에 맞는 기록이 없을 때 그 기간에 지출·수입이 없었다는 뜻으로 표시해서는 안 된다 | M |
| `FR-VIEW-08` | 시스템은 사용자가 분류별 기간 예산을 정할 수 있게 해야 한다 | S |
| `FR-VIEW-09` | 시스템은 정해진 예산과 같은 기간의 실제 지출을 대비해 제시해야 한다 | S |
| `FR-VIEW-10` | 시스템은 기록을 파일로 반출할 수 있게 해야 한다 | S |
| `FR-VIEW-11` | 시스템은 반출한 파일로부터 기록을 반입할 수 있게 해야 한다 | C |
| `FR-VIEW-12` | 시스템은 달력에서 쉬는 날(일요일과 국가가 정한 공휴일)을 다른 날과 구별해 제시해야 한다 | S |
| `FR-VIEW-13` | 시스템은 사용자가 한 줄로 적은 조회 요청을 조건으로 바꾸어 그 조건에 맞는 기록을 찾을 수 있게 해야 한다 | S |

## 6. 품질 요구사항

정확한 합격선은 **SRS §3이 소유한다.** 이 표는 무엇을 어떤 방향으로 확인할지만
정한다.

| ID | 요구 | 우선순위 | 검증 방향 |
|---|---|---|---|
| `NFR-ENTRY-01` | 입력을 제출한 뒤 기록 후보가 제시될 때까지 사용자를 기다리게 하지 않아야 한다 | M | 입력 제출부터 후보 제시까지의 시간 측정. 합격선은 SRS §3이 소유 |
| `NFR-ENTRY-02` | 자동 해석의 결과가 사용자의 의도와 얼마나 일치하는지 측정할 수 있어야 한다 | M | 표본 입력에 대해 항목별 일치 여부를 집계. 합격선은 SRS §3이 소유 |
| `NFR-ENTRY-03` | 외부 해석 수단이 응답하지 않는 상황을 사용자가 알 수 있어야 한다 | M | 응답 불가 상황을 만들고 사용자에게 전달되는 내용을 확인 |

## 7. 제약

### 7.1 MRD에서 계승한 제약

| 구분 | 제약 | 요구에 미치는 영향 |
|---|---|---|
| 법적 | 금융기관 자동 연동은 허가받은 사업자만 할 수 있다 (MRD §6.1) | §3.2 비범위를 강제한다. 대체 경로가 `FR-ENTRY-01`·`FR-ENTRY-04`다 |
| 법적 | 개인 용도와 배포는 적용 전제가 다르다 (MRD §6.1) | 배포는 비범위지만, 전제가 바뀔 수 있음을 `FR-ENTRY-15`·`NFR-ENTRY-05`가 미리 지킨다 |
| 법적 | 외부 인공지능 서비스에 개인정보를 넘기는 처리에는 감독기관이 제시한 기준이 있다 (MRD §6.1) | `FR-ENTRY-15`·`FR-ENTRY-16`의 근거 |
| 운영 | 혼자 만들고 혼자 유지한다 (MRD §6.2) | 운영 손이 계속 가야 하는 요구를 M으로 올리지 않는다 |
| 운영 | 무료로 제공되는 외부 수단은 조건·한도가 바뀔 수 있다 (MRD §6.2) | `NFR-ENTRY-04`(교체 가능성)의 근거 |
| 기술 | 자동 해석은 확률적이며 완전한 정확도를 전제할 수 없다 (MRD §6.3) | `FR-ENTRY-05`·`FR-ENTRY-06`·`FR-ENTRY-07`의 근거 |
| 기술 | 외부 수단에 연결할 수 없는 시간이 존재한다 (MRD §6.3) | `FR-ENTRY-14`·`NFR-ENTRY-03`의 근거 |

### 7.2 이번 개발의 제약

- **기한**: 외부에서 주어진 마감이 없다. 따라서 일정 압박을 이유로 우선순위를
  뒤집지 않는다. M을 줄이는 판단은 §8의 수용 원칙에 따른다.
- **자원**: 개발과 유지가 한 사람에게 있다. 인력이 늘어난다는 전제의 요구는 두지
  않는다.
- **비용**: 유료 계약을 전제하지 않는 조건에서 시작한다. 비용이 드는 수단에
  의존해야만 성립하는 요구는 이번 범위에 두지 않는다.

## 8. 검증과 수용 원칙

판정 원칙을 착수 전에 여기서 공개한다. **결과를 보고 뒤에 완화하지 않는다.**

1. **M 요구는 전부 충족되어야 수용한다.** 하나라도 충족되지 않으면 S·C의 충족
   개수로 상쇄하지 않는다.
2. **금지 요구는 "일어나지 않음"으로 판정한다.** `FR-ENTRY-05`·`FR-ENTRY-15`·
   `FR-CAT-06`·`FR-CAT-08`·`FR-VIEW-07`은 금지된 동작이 관찰되지 않아야 충족이다.
   관찰하지 못한 것과 일어나지 않은 것은 다르므로, 판정 방법을 SRS·TC가 명시한다.
3. **수치 합격선은 SRS §3이 소유한다.** 이 문서는 어떤 수치도 합격선으로 쓰지
   않는다. 승인되지 않은 값은 합격 판정에 쓰지 않는다.
4. **자동 해석의 정확도는 수용 조건이 아니다.** 정확도가 낮아도 사용자가 확인
   단계에서 고칠 수 있으면 요구는 충족된다. 정확도는 측정 대상(`NFR-ENTRY-02`)이며,
   합격선의 승인 여부는 측정 뒤에 판단한다.
5. **문서 정합과 검증은 다른 상태다.** 요구가 문서에 적혔다는 것과 지켜졌다는
   것은 다르며, 후자는 TC와 실행 결과가 판정한다.

### 성과 질문 (MRD §7 계승)

| 성과 질문 | 확인할 결과 |
|---|---|
| 기록이 이어지는가 | 쓰기 시작한 뒤 기록이 끊긴 기간이 어떻게 변하는가 |
| 한 줄로 적는 것이 손으로 넣는 것보다 실제로 덜 번거로운가 | 같은 내용을 두 방식으로 남길 때 드는 수고의 비교 |
| 자동 해석의 결과를 사람이 얼마나 고쳐야 하는가 | 확인 단계에서 사람이 손대는 항목이 무엇이며 시간이 지나며 어떻게 달라지는가 |
| 처음 열었을 때 무엇을 하는 도구인지 알 수 있는가 | 배우는 과정 없이 첫 기록에 도달하는지 관찰 |
| 기록이 되짚어 보는 일로 이어지는가 | 기록만 남기고 마는지, 기간별 요약을 실제로 열어 보는지 |
| 분류가 사용자의 기준으로 유지되는가 | 처음 만든 분류가 계속 쓰이는지, 매번 고쳐 넣게 되는지 |
| 기록을 잃을 걱정 없이 쓸 수 있는가 | 반출한 기록만으로 되살릴 수 있는지 |

# RFP 작성 가이드 (RFP_guide)

> 내부 제안요청서(RFP)는 **"이번 개발에서 무엇을 요구하는가"**를 계약의 무게로
> 확정하는 문서다. 범위(In/Out)를 정하고, **요구 번호 FR·NFR이 여기서 태어난다.**
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 확정된 MRD
- **출력**: 범위/비범위, `FR-<COMP>-NN` 기능 요구, `NFR-<COMP>-NN` 품질 요구, 우선순위
- **다음 문서**: PRD가 FR을 사용자 스토리로, SRS가 같은 FR·NFR 번호를 검증
  가능한 문구로 정련한다

## 2. 작성 전 준비 (필수)

1. **컴포넌트 약칭 확정** — 기능 영역을 1~3개의 컴포넌트로 나누고 `<COMP>`
   약칭(영대문자)을 정한다. 이 약칭이 FR·NFR·TC 번호의 네임스페이스가 되므로
   여기서 확정하고 이후 변경하지 않는다. 실습 규모에서는 1개로 시작해도 된다.
   **요구를 나누는 축과 TC 문서를 나누는 축은 같아야 한다.** 축이 갈라지면
   추적표가 N:M이 되어 사람이 유지할 수 없다.
2. **MRD 대조** — 각 요구가 MRD의 어떤 문제·범위에서 나왔는지 연결할 수 있는지
   확인한다. MRD에 근거가 없는 요구는 만들지 않는다(필요하면 MRD를 먼저 고친다).
3. **규모는 상위 문서가 정한다** — 요구 개수는 MRD 범위 표에서 나온다. 범위 한
   줄이 요구 여럿을 낳을 수는 있어도, MRD에 없는 요구가 생길 수는 없다. 적정
   개수를 정해 두고 거기에 맞추지 않는다 — 개수를 맞추려 요구를 합치면 원자성이
   깨진다. 요구가 유난히 많아지면 줄이지 말고 **컴포넌트를 나눌 때**가 됐는지 본다.

## 3. 문서 골격

```
헤더 표: 문서 역할 · 버전 · MRD 기준(버전 링크) · 상태(Draft)
## 1. 문서 목적과 경계     이 문서가 답하는 질문 불릿 + 답하지 않는 것
                          ("이 문서는 특정 API·DB·클래스·모델을 규정하지 않는다" 명시)
## 2. 상위 문제와 방향     MRD 요약 2~3문장 + 제품이 보존해야 할 원칙(번호 목록)
## 3. 범위와 비범위        3.1 범위 표(범위|제공해야 하는 결과) / 3.2 비범위 불릿
                          비범위는 이 문서가 소유한다. PRD·SRS는 인용만 하고,
                          추가가 필요하면 여기를 먼저 고친다
## 4. 전체 흐름            입력부터 결과까지 end-to-end 흐름을 번호 목록으로
## 5. 기능 요구사항        FR 표. 컴포넌트별 하위 절로 나눈다
                          | ID | 요구 | 우선순위 |  (FR-<COMP>-01부터)
## 6. 품질 요구사항        표: | ID | 요구 | 우선순위 | 검증 방향 |
                          (`NFR-<COMP>-01`부터.
                          성능·신뢰성·보안·사용성·유지보수성 등. 정확한 합격선은
                          SRS §3이 소유함을 명시)
## 7. 제약                MRD 제약 중 개발 요구에 영향을 주는 것 +
                          이번 개발의 기한·자원 제약(MRD에 없던 것이면 여기서 처음 적는다)
## 8. 검증과 수용 원칙     어떤 원칙으로 수용을 판정할 것인가 + 성과 질문 표(MRD §7 계승)
                          판정 원칙은 착수 전에 여기서 공개한다. 결과를 보고 뒤에 완화하지 않는다
## 9. 추적성              표 위에 체인 한 줄:
                          `MRD → **RFP**(FR·NFR 탄생) → PRD → SRS → TC → test`
                          | MRD 근거 | 본 RFP FR·NFR | 하위 문서(예정) |
                          표 아래에 **검수 합계 한 줄**을 남긴다(§6에서 센 숫자)
## 10. 변경 이력          | 버전 | 날짜 | 변경 요약 | 영향 요구(FR·NFR ID) |
                          오탈자 수정과 요구 변경을 구분해 적는다
## 11. 미결 사항          | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
                          결정된 항목은 지우지 말고 Decided로 바꾸고 반영 위치를 적는다
```

## 4. 작성 규칙

- **요구 문형**: "시스템은 ~을 제공해야 한다 / ~하게 해야 한다" — 관찰 가능한
  결과를 요구한다. 구현 방법("~를 사용해서")은 쓰지 않는다.
- **우선순위 필수**: `M`(이번에 반드시) / `S`(목표하되 조정 가능) / `C`(선택).
  전부 M이면 우선순위가 없는 것과 같다 — 하나도 뺄 수 없다면 범위가 과한 것이다.
- **FR은 결과 단위로**: 하나의 FR은 하나의 제공 결과를 말한다. "A하고 B해야
  한다"는 쪼갠다.
- **금지 요구도 요구다**: "~하지 않아야 한다"(자동 확정 금지 등)는 중요한
  계약이므로 FR로 명시한다.
- **비범위를 아끼지 않는다**: 오해할 만한 기능은 비범위에 명시한다. 비범위는
  "이번에 약속하지 않는다"이지 열등함이 아니다.
- **"나중에"와 "안 함"을 섞지 않는다**: 비범위는 이번 개발에서 약속하지 않는
  것이고, 다음 차수 계획은 아직 요구가 아니다. 검증되지 않은 아이디어를 `M`
  요구로 올리지 않는다.
- 번호는 `FR-<COMP>-01`·`NFR-<COMP>-01`부터 이어 붙인다. 두 가족 모두 README §2의
  append-only 규율(재사용 금지, 폐기는 취소선+대체 포인터)을 그대로 따르고,
  SRS가 **같은 번호로** 정련한다.
- **1:N으로 쪼개질 요구는 여기서 미리 쪼갠다**: 하나의 요구가 SRS에서 여러 개로
  갈라져야 할 것 같으면 SRS에서 새 번호를 만들지 말고, RFP에서 먼저 나눈다.
  번호 관통이 깨지는 지점이 곧 번역표가 필요해지는 지점이다.

### 요구 문장 예시

요구 문장이 부적합해지는 세 가지 유형이다.

| 유형 | ✗ | ✓ |
|---|---|---|
| 구현 방법을 지정 | 색인 엔진에 제목·저자를 색인해 검색해야 한다 | 입력 키워드와 일치하는 도서를 관련도 순으로 반환해야 한다 |
| 한 요구에 두 가지 | 결과를 목록으로 보여주**고** 대출 상태**도** 표시해야 한다 | 두 요구로 쪼갠다 |
| 금지 요구의 누락 | (해당 서술이 없음) | 결과가 없을 때 장서에 없다는 뜻으로 표시**해서는 안 된다** |

아래 요구가 이후 모든 가이드에서 사용하는 표준 예제다.

**골격 §5 기능 요구**

| ID | 요구 | 우선순위 |
|---|---|---|
| `FR-LIB-01` | 시스템은 입력 키워드와 일치하는 도서를 관련도 순으로 반환해야 한다 | M |
| `FR-LIB-02` | 시스템은 검색 결과가 없을 때 해당 도서가 장서에 없다는 뜻으로 표시해서는 안 된다 | M |

**골격 §6 품질 요구**

| ID | 요구 | 우선순위 | 검증 방향 |
|---|---|---|---|
| `NFR-LIB-01` | 검색 결과가 담당자를 기다리게 하지 않아야 한다 | S | 요청→응답 시간 측정. 합격선은 SRS §3이 소유 |

## 5. 금지 사항

- 코드 경로, 클래스·함수명, DB 테이블, 포트, 모델 식별자, 화면 상세
- 구현 상태 표기(README §5) / 근거 없는 성능 수치를 합격선으로 쓰는 것
- MRD에 근거가 없는 요구의 신설
- 사용자 스토리(PRD 영역), 검증 절차(TC 영역)의 상세 전개
- `FR`·`NFR` 밖의 새 ID 가족 신설 — 요구 종류가 더 필요해 보이면 만들지 말고
  미결 사항에 질문으로 남긴다

## 6. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] 모든 요구가 `FR-<COMP>-NN`·`NFR-<COMP>-NN` 형식이고 번호가 연속·중복 없다
      → 센 결과를 골격 §9 합계 줄에 적는다:
        `FR __개(01~__) / NFR __개(01~__) / 빠짐 __ / 중복 __`
- [ ] `FR`·`NFR` 밖의 ID 가족을 만들지 않았다
- [ ] 모든 요구에 우선순위(M/S/C)가 있다 (우선순위 칸이 빈 행 0개)
- [ ] 우선순위가 전부 M은 아니다
      (M이 100%면 무엇을 S로 내릴 수 있는지 다시 판단한다)
- [ ] 각 요구가 관찰 가능한 결과 문형이고 구현 방법을 지정하지 않는다
      (요구 문장에서 "~를 사용해"·"~로 구현"과 라이브러리·DB·모델 고유명사를
      검색해 0건인지 확인)
- [ ] 한 요구가 두 가지 이상을 요구하지 않는다
      (요구 문장에서 "그리고"·"하며"·"및"을 검색해 걸린 행을 하나씩 재검토.
      쉼표는 단순 나열에도 쓰이므로 검색어에 넣지 않는다)
- [ ] 범위와 비범위가 모두 명시됐다 (오해를 부를 기능이 비범위에 적혔는지 확인)
- [ ] 금지 요구("~해서는 안 된다")가 최소 하나 있다
      (하나도 없으면 오해를 부를 동작을 아직 못 짚은 것이다)
- [ ] 추적성 표에서 모든 요구가 MRD 근거와 연결된다
      → 센 결과를 골격 §9 합계 줄에 적는다: `요구 __개 / 추적 __행 / 누락 __개`

# MRD 작성 가이드 (MRD_guide)

> MRD(Market Requirements Document, 시장 요구 문서)는 **"왜 이 제품을 만드는가"**에
> 답하는 최상위 출발 문서다. 해결책이 아니라 **문제**를 확정한다.
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 이 가이드의 §2 조사 결과. MRD가 사실로 적는 것은 전부 여기서 나온다.
- **주제**: 무엇에 대한 MRD인지는 밖에서 온다. 주제를 정할 뿐 내용의 근거는
  아니며, 주제가 정해지면 역할이 끝난다.
- **출력**: 문제 정의·대상 사용자·범위 방향·제약·성공 질문 — 이후 RFP가 요구로 전개한다
- **다음 문서**: RFP가 MRD의 문제·범위·제약을 기능 요구(FR)와 품질 요구(NFR)로
  전개한다

## 2. 작성 전 조사 (필수)

웹 검색으로 다음을 조사한 뒤 초안을 시작한다. 검색 도구를 쓸 수 없는 세션이면
§2 결과를 `[조사 미수행]`으로 표시하고 상태를 `Draft`에 묶어 둔다(Review로
올리지 않는다). 조사 없이 작성한 MRD는 근거가 아니라 추정에 기반한 문서이므로
이 가이드의 요건을 충족하지 않는다.

1. **문제의 실재 근거** — 이 문제가 실제로 존재하고 반복된다는 통계·보도·조사.
2. **대상 사용자** — 누가 이 문제를 겪는가. 역할과 이용 맥락.
3. **기존 대안과 한계** — 지금은 이 문제를 어떻게 해결하고 있으며 무엇이 부족한가.
   경쟁 제품뿐 아니라 "수작업으로 버틴다"도 대안이다. 결과는 골격 §2에 녹인다.
4. **규제·법령·정책** — 이 도메인에 적용되는 법적 제약이 있는가(개인정보, 산업 규제 등).
   해당 법령·가이드라인의 공식 원문 링크를 확보한다.

### 근거 사다리

위 등급부터 순서대로 확보하고, 사용한 등급을 본문 문장에 드러낸다.

| 등급 | 출처 | 본문에 쓰는 방식 |
|---|---|---|
| 1 | 공식 기관 통계·법령·연차보고서 | 그대로 사실로 서술 |
| 2 | 업계 리포트·언론 보도·학술 조사 | 출처 주체를 문장에 밝힌다("~의 조사에 따르면") |
| 3 | 유사 도메인의 대리 지표 | **대리 지표임을 문장에 명시**하고 한계를 한 줄 붙인다 |
| 4 | 못 찾음 | `[확인 필요]` — **어떻게 확인할지**까지 적는다 |

- **URL은 실제로 열어 확인한 것만 쓴다.** 기억에 의존해 주소를 임의로 작성하지
  않는다. 확인하지 못한 근거는 등급 4로 분류한다.
- 각주 형식: `기관·저자, 「제목」, 발행일, 매체. <URL> (접속 YYYY-MM-DD)`.
  법령은 시행일을 함께 적는다.
- 통계는 원칙적으로 5년 이내. 더 오래된 자료를 쓰면 이유를 한 줄 붙인다.
- **골격 §2의 핵심 주장 중 최소 하나는 등급 1~2여야 한다.** 전부 3~4로 채워지면
  주제가 너무 넓거나 모호한 것이므로, 초안을 넘기지 말고 주제를 좁혀 다시 조사한다.

조사에서 확보하지 못한 수치는 쓰지 않는다. 어디서 들어온 주장이든 — 사람이 말한
것이라도 — 조사로 확인되지 않으면 사실로 적지 않고 `[확인 필요]`로 표시한다.

## 3. 문서 골격

```
헤더 표: 문서 역할 · 버전 · 작성일 · 상태(Draft)
## 1. 문서 목적           이 문서가 답하는 것 / 답하지 않는 것(→ 다음 문서 표)
## 2. 문제 정의           어떤 문제가 왜 반복되는가. 근거 수치는 각주로.
                         현재 방식과 기존 대안의 병목을 불릿으로(조사 항목 3의 결과).
                         "핵심 필요는 ~이 아니라 ~에 있다" 한 줄
## 3. 대상 사용자와 맥락   직접 사용자 표(사용자|수행하는 일) + 제품 밖 이해관계자 구분
## 4. 제품 방향           비전 한 문단 + 핵심 원칙(보통 3~7개, 번호 목록)
                         ※ 방향까지만. 기능 상세·화면·기술은 쓰지 않는다
## 5. 범위와 비범위       범위 표 + 비범위 불릿. 비범위는 약속하지 않는 것의 명시
                         (이 비범위가 RFP §3.2로 계승된다)
## 6. 제약               법적·운영적·기술적 제약을 나눠 서술. 도입자가 별도로
                         확정해야 하는 사항을 구분
## 7. 성공 결과           성과 질문 표(성과 질문|확인할 결과). 수치 합격선은 만들지 않고
                         "무엇으로 성공을 확인할 것인가"를 질문으로 고정
## 8. 다음 문서 연결과 References   RFP로 넘어갈 항목 + 각주 출처 목록
## 9. 변경 이력           | 버전 | 날짜 | 변경 요약 | 영향 범위 |
                         오탈자 수정과 방향 변경을 구분해 적는다
## 10. 미결 사항          | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
                         본문의 모든 `[확인 필요]`와 사람에게 물을 것을 여기 모은다.
                         결정된 항목은 지우지 말고 Decided로 바꾸고 반영 위치를 적는다
                         표 아래에 **검수 합계 한 줄**을 남긴다(§6에서 센 숫자)
```

## 4. 작성 규칙

아래에서 `골격 §N`은 §3 문서 골격의 절 번호이고, 그냥 `§N`은 이 가이드의 절이다.

- **문제 중심으로 쓴다.** "~기능이 필요하다"가 아니라 "~한 상황에서 ~한 문제를
  겪는다"로 쓴다. 기능 목록이 나오기 시작하면 RFP의 영역을 침범한 것이다.
- **해결책은 방향 수준에서 멈춘다.** 골격 §4의 원칙은 "무엇을 우선하는가"의
  선언이지 구현 방식이 아니다. 특정 기술·모델·아키텍처를 지정하지 않는다.
- **근거로 절실함을 보인다.** "~할 것 같다"가 아니라 "~라는 조사가 있다"로 쓴다.
- **성공은 질문으로 남긴다.** 측정 데이터가 없는 시점이므로 목표 수치를 만들지
  않고, 나중에 무엇을 측정해 확인할지를 질문 형태로 고정한다.
- **간결하게 쓴다.** 조사 원자료가 길면 본문에 옮기지 말고 `docs/research/`에
  따로 남기고 결론과 링크만 싣는다. MRD는 실행 가능한 요약이지 조사
  보고서가 아니다.
- 독자는 기술자만이 아니다. 기술 용어 없이 읽히게 쓴다.

### 문장 예시

| 골격 | ✗ 부적합한 문장 | ✓ MRD의 문장 |
|---|---|---|
| §2 문제 정의 | 키워드 검색 **기능이 없어** 불편하다 | 이용자는 제목을 정확히 기억하지 못한 채 서가를 훑고, 사서에게 같은 질문을 반복한다[^1] |
| §4 핵심 원칙 | 검색은 색인 엔진으로 처리해 200ms 이내로 유지한다 | **찾지 못한 것과 없는 것을 구분한다.** 결과가 비었을 때 장서에 없다는 뜻으로 표시하지 않는다 |
| §7 성공 결과 | 검색 성공률 90% 이상 달성 | 이용자가 사서를 거치지 않고 자료에 도달하는가 \| 사서 문의 건수 변화로 확인 |

✗ 항목은 각각 **기능 요청 · 구현 선택 · 미측정 수치**에 해당하며, 모두 MRD의
경계를 벗어난 서술이다. §4의 원칙은 다음 문서에서 `FR-LIB-02`로 전개된다
(README §1의 관통 표 참조).

## 5. 금지 사항

- API, 데이터 구조, 화면 구성, 모델·라이브러리 이름, 성능 수치 목표
- 출처 없는 시장 통계, 지어낸 경쟁 분석, 열어 확인하지 않은 URL
- 구현 상태 표기(README §5) — "이미 구현된", "지원 예정" 등

## 6. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] 모든 수치·주장에 각주 출처가 있다
      (본문의 숫자를 전부 세어, 각주도 `[확인 필요]`도 없는 숫자가 0개인지 확인)
- [ ] 인용한 URL을 전부 실제로 열어 확인했다
      (열지 못한 것은 등급 4로 내리고 `[확인 필요]`로 바꿨는지 확인)
- [ ] 핵심 주장 중 최소 하나가 근거 등급 1~2다
      (전부 3~4면 넘기지 말고 주제를 좁혀 재조사)
- [ ] 기능 목록·구현 상세가 없다
      (골격 §2~§4·§6~§7에서 "버튼"·"화면"·"API"·"DB"와 라이브러리·모델
      고유명사를 검색해 0건인지 확인. **골격 §5 비범위는 "안 만들 기능"을 적는
      곳이므로 검사 대상에서 뺀다**)
- [ ] 범위와 비범위가 모두 명시되어 있다
      (오해를 부를 만한 항목이 비범위에 적혔는지 — 개수가 아니라 누락을 본다)
- [ ] 성공 결과가 수치 합격선이 아니라 확인 질문으로 적혀 있다
      (골격 §7 표에 숫자와 부등호가 0건인지 확인)
- [ ] 조사 원자료를 본문에 옮기지 않고 결론과 링크만 실었다
- [ ] 본문의 모든 `[확인 필요]`가 골격 §10 미결 사항 표에 올라가 있다
      → 센 결과를 골격 §10 아래 합계 줄에 적는다:
        `본문 [확인 필요] __개 / 미결 Open __행`
- [ ] 다음 문서(RFP)로 넘어갈 항목이 골격 §8에 정리되어 있다

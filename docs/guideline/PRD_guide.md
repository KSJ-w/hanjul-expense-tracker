# PRD 작성 가이드 (PRD_guide)

> PRD(Product Requirements Document, 제품 요구 문서)는 **"사용자가 어떤 경험을
> 얻는가"**에 답한다. RFP의 요구를 사용자 관점의 과업·여정·수용 조건으로 풀어쓴다.
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 확정된 MRD·RFP
- **출력**: 사용자 역할, end-to-end 여정, 에픽/사용자 스토리(US), Given-When-Then
  수용 조건 — 모든 수용 조건이 RFP의 FR(해당하면 NFR) 번호와 연결된다
- **다음 문서**: SRS가 수용 조건을 검증 가능한 시스템 요구로 정련하고, 그 요구를
  TC가 시험 절차로 옮긴다. **Then이 관찰 가능해야 하는 이유가 이것이다** —
  관찰 지점이 없는 Then은 나중에 시험으로 옮길 수 없다

## 2. 작성 전 준비 (필수)

1. RFP의 FR 전체 목록을 뽑아 둔다 — 이 PRD가 끝났을 때 **모든 Active FR이
   최소 하나의 스토리 또는 절에 파생**되어야 한다(추적표로 확인).
2. **RFP의 NFR을 분류한다** — NFR은 전부 스토리가 되지는 않는다.
   - 사용자에게 **보이는** NFR(성능·사용성 등) → 수용 조건의 Then에 반영하고
     추적표에 연결한다.
   - 사용자에게 **보이지 않는** NFR(유지보수성·이식성 등) → PRD를 건너뛰고
     SRS로 직행한다. 추적표에 `PRD 해당 없음(SRS 직행)`으로 적는다.
   빠뜨리는 것과 건너뛰는 것은 다르다. 건너뛴 것도 표에 적혀야 누락이 아니다.
3. 사용자 역할을 확정한다 — 실제 소프트웨어 역할(로그인해서 쓰는 사람)과
   제품 밖 이해관계자를 구분한다.
4. **규모는 역할과 과업이 정한다** — 스토리 수는 사용자 역할 × 핵심 과업에서
   나온다. 정해 둔 개수에 맞추려고 스토리를 쪼개거나 합치지 않는다.

## 3. 문서 골격

```
헤더 표: 문서 역할 · 버전 · MRD/RFP 기준(버전 링크) · 상태(Draft)
## 1. 문서 목적과 경계     이 문서가 답하는 질문 불릿 + 두지 않는 것
                          (API 필드·화면 상세·시험 fixture는 하위 문서 소유 명시)
## 2. 사용자 역할          2.1 직접 사용자 표(역할|목표|수행 책임)
                          2.2 외부 이해관계자 표(제품 역할 아님을 명시)
                          2.3 역할별 접근 표(과업 × 역할 허용/불가)
## 3. 보존할 제품 원칙과 범위   원칙 번호 목록(RFP §2 계승) + 비범위(RFP §3.2 계승)
## 4. end-to-end 사용자 여정    역할별로 번호 스텝. 정상 흐름 + 권한·실패·복구 여정 표
                          (상황|제품이 보여줄 의미|사용자의 다음 행동)
## 5. 에픽과 사용자 스토리
   ### EPIC-01 — <이름>
   #### US-01-01 — <제목> (P0/P1/P2)
   > As <역할>로서 / I want <무엇을> / So that <왜·어떤 가치>
   - 사용자: <역할>   · 연계 RFP: FR-<COMP>-NN (해당하면 NFR-<COMP>-NN)
   수용 조건:
   1. **Given** <전제> **When** <행동>
      **Then** <관찰 가능한 결과> (FR 또는 NFR 번호)
## 6. 상태·오류 모델       표: 상태|사용자 의미|제품의 수용 결과
                          (입력 미완료·권한 부족·진행 중·부분 실패·빈 결과·처리 실패)
## 7. 성공 지표            성과 질문 표 + 현재 검증 상태("측정 필요" 등 정직하게)
## 8. RFP 추적성          표 위에 체인 한 줄:
                          `MRD → RFP(FR·NFR) → **PRD**(EPIC/US) → SRS → TC → test`
                          | RFP FR·NFR | 본 PRD EPIC/US | 파생 상태 |
                          NFR 중 SRS로 직행하는 것은 `PRD 해당 없음(SRS 직행)`으로 적는다
                          표 아래에 **검수 합계 한 줄**을 남긴다(§6에서 센 숫자)
## 9. 변경 이력           | 버전 | 날짜 | 변경 요약 | 영향 범위 |
## 10. 미결 사항          | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
```

## 4. 작성 규칙

- **스토리 형식**: As(누가) / I want(무엇을) / So that(왜)를 채운다. 사용자
  가치가 안 나오는 스토리는 스토리가 아니다.
- **수용 조건은 Given-When-Then**으로, 결과는 화면·응답에서 관찰 가능해야 한다.
  (상위 문서 PRD_survey의 "수용 기준"과 같은 것이다 — 이 가이드는 "수용 조건"으로
  통일해 쓴다.)
  수용 조건이 많아지는 것은 스토리가 크다는 **신호**다 — 정상 경로만으로 여러
  개가 나오면 쪼갤 수 있는지 검토한다. 개수 자체는 합격 기준이 아니다.
- **모든 Then에 요구 번호**를 단다 — 기능이면 FR, 사용자에게 보이는 품질이면
  NFR. 연결할 요구가 없으면 누락된 것이므로 RFP에 먼저 추가한 뒤 진행한다
  (임의로 스토리만 만들지 않는다).
- **오류·빈 결과도 경험이다**: 잘못됐을 때 사용자가 무엇을 보고 무엇을 할 수
  있는지를 정상 흐름과 같은 비중으로 쓴다. 특히 "빈 결과"에 금지되는 해석
  (예: 결과 없음 ≠ 대상 없음)을 명시한다.
- **우선순위**: `P0`(핵심 여정에 필수) / `P1`(보조) / `P2`(후속·선택).
  RFP의 M/S/C와 1:1로 대응시킨다 — M↔P0, S↔P1, C↔P2. 대응이 어긋나면 둘 중
  하나가 틀린 것이므로 RFP를 먼저 확인한다.
- **US·EPIC 번호는 요구 ID가 아니다**: `EPIC-NN`·`US-<에픽>-<순번>`은 이 문서의
  구조 번호이고, 요구는 어디까지나 인용한 FR·NFR이다. 다만 번호 규율은 같다 —
  재사용·재배치하지 않고 폐기는 취소선과 대체 포인터로 남긴다.
- 화면 스펙이 아니다. 버튼 위치·색·레이아웃이 아니라 행동과 관찰 결과를 쓴다.

### 스토리 예시

RFP의 `FR-LIB-01`·`FR-LIB-02`·`NFR-LIB-01`을 사용자 스토리로 전개한 예다.

```markdown
#### US-01-01 — 키워드로 도서 찾기 (P0)

> **As** 도서관 이용자로서 **I want** 기억나는 단어만으로 도서를 찾고
> **So that** 제목을 정확히 몰라도 서가를 훑지 않아도 된다

- 사용자: 이용자   · 연계 RFP: FR-LIB-01, FR-LIB-02, NFR-LIB-01

**수용 조건**
1. **Given** 장서에 해당 도서가 있을 때 **When** 제목 일부로 검색하면
   **Then** 그 도서가 결과 목록에 표시되어야 한다 (FR-LIB-01)
2. **Given** 여러 도서가 일치할 때 **When** 검색하면
   **Then** 더 많이 일치한 도서가 위에 오도록 정렬되어야 한다 (FR-LIB-01)
3. **Given** 일치하는 도서가 없을 때 **When** 검색하면
   **Then** 결과 없음으로 표시하되 장서에 없다고 단정해서는 안 된다 (FR-LIB-02)
4. **Given** 장서 규모가 운영 조건일 때 **When** 검색하면
   **Then** 결과가 SRS §3이 정한 응답 시간 안에 표시되어야 한다 (NFR-LIB-01)
```

3번이 **실패·빈 결과 경로**, 4번이 **보이는 NFR을 Then에 다는 방식**이다 —
수치는 인용하지 않고 합격값 소유자(SRS §3)를 가리킨다. 정상 경로만 나열하면
스토리를 반만 정의한 것이다.

**부적합한 수용 조건**

| ✗ | 문제점 |
|---|---|
| Then 검색이 잘 동작해야 한다 | 관찰 지점이 없어 무엇을 확인해야 하는지 알 수 없다 |
| Then 검색 API가 200과 배열을 반환해야 한다 | 구현 상세. SRS·SDD 영역이다 |
| As 이용자로서 I want 검색하고 싶다 | So that이 없다. 사용자 가치가 드러나지 않으면 스토리가 아니라 기능 목록이다 |

## 5. 금지 사항

- API 필드, DB 구조, 내부 프로세스, 모델 이름, 폴링 주기 같은 구현 상세
- FR 연계 없는 수용 조건, RFP 비범위 기능의 스토리화
- 이 문서에서 새 비범위를 만드는 것 — 비범위는 RFP §3.2가 소유한다.
  추가가 필요하면 RFP를 먼저 고친다
- 구현 상태 표기(README §5) / 측정 없는 성능 수치의 목표화
- 시험 절차의 상세 전개(TC 영역)

## 6. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] 모든 스토리에 As/I want/So that 세 줄이 다 있다 (빈 줄이 있는 스토리 0개)
- [ ] 모든 스토리에 사용자·연계 FR·우선순위가 있다
- [ ] 모든 수용 조건이 Given-When-Then이고 Then마다 요구 번호(FR 또는 NFR)가 있다
      → 센 결과를 골격 §8 합계 줄에 적는다: `Then __개 / 요구 번호가 붙은 Then __개`
- [ ] 정상 경로만 있는 스토리가 없다
      (스토리마다 실패·권한·빈 결과 중 최소 하나의 수용 조건이 있는지 확인)
- [ ] RFP의 모든 Active FR이 추적표에서 최소 한 곳에 파생됐다
      → 센 결과를 골격 §8 합계 줄에 적는다: `RFP Active FR __개 / 추적표 __행 / 누락 __개`
- [ ] RFP의 모든 NFR이 추적표에 있다
      (스토리에 반영했거나 `PRD 해당 없음(SRS 직행)`으로 적혀 있다)
      → 센 결과를 골격 §8 합계 줄에 적는다: `RFP NFR __개 / 추적표 __행 / 누락 __개`
- [ ] 우선순위가 RFP의 M/S/C와 어긋나지 않는다 (M↔P0, S↔P1, C↔P2)
- [ ] 오류·권한·빈 결과·부분 실패의 사용자 경험이 정의됐다
      (골격 §6 표의 여섯 상황이 모두 채워졌는지 확인)
- [ ] "빈 결과"에 금지되는 해석이 명시됐다 (결과 없음 ≠ 대상 없음)
- [ ] 화면 상세·구현 상세가 없다
      (본문에서 "버튼"·"색"·"레이아웃"·"API"·"DB"·상태코드 숫자를 검색해 0건인지 확인)

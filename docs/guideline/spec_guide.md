# Spec 기반 개발 운영 가이드 (spec_guide)

> **무엇인가.** 문서 체인·에이전트 컨텍스트·검증 자동화를 하나의 체계로 운영하는
> 개발 방식을, 이 파일 하나로 새 프로젝트에 구축할 수 있게 정리한 종합 가이드다.
> 문서별 상세 작성법은 `MRD_guide.md` 등 개별 가이드가 다루지만, 구조와 역할과
> 운영 규칙은 이 문서만으로 갖출 수 있다.
>
> **목적은 하나다.** "이 코드가 어떤 요구를 지키고 있는가"를 번호로 언제나
> 대답할 수 있게 하는 것.

## 0. 핵심 규칙 요약

이것만 지켜도 방법론의 대부분이 성립한다.

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 요구 ID는 한 번 붙이면 바꾸지 않는다 (append-only, 재사용 금지) | 번호가 흔들리면 추적성 전체가 무너진다 |
| 2 | 같은 `FR-<COMP>-NN`·`NFR-<COMP>-NN`이 RFP→SRS를 관통한다 | 문서 사이 번호 대조표가 필요 없어진다 |
| 3 | 요구 문서에 구현 상태를 섞지 않는다 | 요구=보장할 것, 상태=리포트·git이 안다 |
| 4 | 테스트에 TC ID를 태깅하고 리포트가 문서와 대조한다 | 드리프트를 사람 기억이 아니라 기계가 잡는다 |
| 5 | 코드 변경 커밋에 문서·테스트를 같이 담는다 | 나중에 몰아서 하면 영원히 안 한다 |
| 6 | 근거 없는 수치를 쓰지 않는다 | "왜 이 값인가"에 문서로 답할 수 있어야 한다 |
| 7 | 컨텍스트 파일은 코드 실제 상태와 항상 일치시킨다 | 틀린 컨텍스트는 없는 것보다 나쁘다 |
| 8 | 문서를 늘리지 말고 각 문서가 자기 역할만 하게 한다 | 중복된 문서는 함께 낡는다 |

## 1. 전체 구조 — 3층

| 층 | 소유자 | 산출물 | 갱신 시점 | 무엇이 맞는가의 기준 |
|---|---|---|---|---|
| ① 에이전트 컨텍스트 | 개발자(에이전트가 읽음) | `.claude/CLAUDE.md`, `.claude/skills/*/SKILL.md` | 코드 변경마다 | 코드 |
| ② 요구 문서 | 사람 | `docs/` 아래 MRD·RFP·PRD·SRS·SDD·TC | 요구 변경마다 | 합의된 내용 |
| ③ 검증 자동화 | 기계 | `test/` + 자동 대조 리포트 | 매 실행 | 실행 결과 |

세 층을 잇는 다리는 두 개다.

- **문서 → 테스트**: `TC-<COMP>-NN`. TC 문서가 정의하고, 테스트 함수가 태깅하고,
  리포트가 양쪽을 집합 비교한다.
- **코드 → 문서**: 커밋 규약. 코드가 바뀌면 같은 커밋에 컨텍스트 파일과 관련
  요구 문서가 따라간다.

> **가장 흔한 실패**: ②요구 문서만 만들고 ①③을 생략하는 것이다. 이 경우 문서는
> 첫 달 이후 갱신되지 않는다. ③이 있으면 문서가 코드와 어긋날 때 CI가 실패를
> 보고하고, ①이 있으면 에이전트가 매 세션 문서의 규칙을 읽는다.

## 2. 저장소 뼈대 (Day 0 — 반나절)

```
프로젝트 루트/
├─ .claude/
│   ├─ CLAUDE.md                  # 항상 로드되는 프로젝트 지도 (§5)
│   └─ skills/<이름>/SKILL.md     # 영역별 전문 지식 (§5, 코드가 커진 뒤 추가)
├─ docs/
│   ├─ GOAL.md                    # 사람이 쓰는 의도 메모 (체인 밖 입력물)
│   ├─ MRD.md  RFP.md  PRD.md  SRS.md  SDD.md
│   ├─ tc/TC_<COMP>.md            # TC는 컴포넌트 단위 파일
│   ├─ report/                    # 측정·실험 보고서 (근거 계층)
│   └─ research/                  # 조사·검증 보고서 (근거 계층)
└─ test/
    ├─ pytest.ini  conftest.py  generate_report.py   # 장치 3파일 (§6)
    └─ test_<comp>.py
```

Day 0 순서:

1. `CLAUDE.md` 작성 — 아키텍처 원칙(불변식) 3~5개부터 쓴다 (§5.1)
2. 컴포넌트 목록과 `<COMP>` 약칭 확정 — **ID 접두어를 여기서 확정한다**.
   소규모는 1~3개면 충분하다. **요구를 나누는 축과 TC 문서를 나누는 축을
   같게 잡는다** — 갈라지면 추적표가 N:M이 되어 손으로 유지할 수 없다
3. 장치 3파일 + CI 워크플로 1개 구성 — `pytest.ini`·`conftest.py`는 부록 A를
   그대로 복사하고, `generate_report.py`는 부록 A의 구현 계약대로 작성한다
   (AI에게 계약을 주고 구현을 맡겨도 된다)
4. 문서 체인은 GOAL부터 순서대로 (§3)

**최소 코어 4개** — 이것만으로 체인이 성립한다. 나머지는 신호가 올 때 늘린다(§9).

1. `CLAUDE.md` (컨텍스트 + 동기화 규칙 표)
2. `FR`·`NFR`·`TC` 세 ID 가족과 append-only 번호 규율
3. TC 태깅 + orphan 자동 검출
4. 문서·테스트를 같이 담는 커밋 규약

## 3. 문서 체인 — 역할과 경계

```
GOAL(사람) → MRD → RFP → PRD → SRS → TC → 테스트 코드
                                └→ SDD (곁가지 · 설계 결정 기록)
```

| 문서 | 답하는 질문 | 포함 | 포함하지 않을 것 |
|---|---|---|---|
| GOAL | 무엇을 왜 만들고 싶은가 | 사람이 자유롭게 쓴 의도 메모 | 정형 양식·ID·분량 제한 — 무엇을 만들고 싶은지만 담기면 된다. 주제를 정할 뿐 MRD 내용의 근거는 아니다 (체인 밖 입력물) |
| MRD | 왜 만드는가 | 문제, 사용자, 범위 방향, 제약, 성공 질문 | 기능 목록, 구현, 수치 목표 |
| RFP(내부 제안요청서) | 무엇을 요구하는가 | 범위 In/Out, `FR-<COMP>-NN`·`NFR-<COMP>-NN` 탄생, M/S/C | 코드 경로, 구현 방법, 상세 설계 |
| PRD | 사용자가 어떤 경험을 얻는가 | 역할, 여정, 스토리+Given-When-Then(모든 Then에 FR) | 화면 상세, DB, 내부 구조 |
| SRS | 무엇을 얼마나 정확히 보장하는가 | 같은 FR·NFR 번호의 검증 가능 정련 + 검증 유형 + **수치 합격선 소유** | 기술 선택 이유, 새 요구 번호 발급 |
| SDD | 어떻게 구현하는가 | 구조, 데이터, 흐름, **설계 결정 기록(ADR)** | 코드 복사, 시장·스토리 반복 |
| TC | 어떻게 증명하는가 | `TC-<COMP>-NN`, 전제·절차·기대·Pass/Fail | 배경 설명, 설계 이유 |

**배치 판정** — 애매한 내용은 위에서 아래로 물어 처음 "예"가 나오는 문서에 쓴다.
① 시장·사용자의 문제인가 → MRD ② 이번에 제공할 결과인가 → RFP ③ 사용자가
보고 수행하는 경험인가 → PRD ④ 시스템이 관찰 가능하게 보장할 동작인가 → SRS
⑤ 구조·기술로 실현하는 방법인가 → SDD ⑥ 합격 확인 방법인가 → TC.

**파생 완전성** — 하위 문서는 상위 문서의 Active 요구를 빠짐없이 파생한다.
PRD가 끝나면 RFP의 모든 FR이 스토리 어딘가에(사용자에게 보이지 않는 NFR은
`SRS 직행`으로 표에 명시), SRS가 끝나면 모든 FR·NFR이 정련되어, TC가 끝나면
모든 시험 유형 요구에 TC가 있어야 한다(각 문서의 추적성 표로 확인).

**SDD는 작게 시작한다** — 설계 결정 기록(ADR) 표
`| ID | 날짜 | 결정 | 검토한 대안 | 선택 이유 | 비용·한계 | 되돌릴 조건 | 상태 |`
하나로 시작하고, 구조·데이터·흐름 절은 조건이 생겼을 때만 추가한다. 바뀐 결정은
지우지 않고 `Superseded(→ADR-0NN)`로 표시하고 새 행을 더한다.

**AI 협업 규칙** — 사람이 GOAL을 쓰고, AI가 각 문서의 가이드 가이드에 따라 초안을
만들고, 사람이 검토·수정한 뒤에만 다음 문서로 넘어간다. AI가 지어낸 수치·근거는
검토 단계에서 걸러낸다. 검토 없는 수용은 문서에서도 금물이다.

## 4. ID 규율과 문서 공통 규약

### 4.1 ID 세 가족

| ID | 태어나는 곳 | 쓰이는 곳 | 의미 |
|---|---|---|---|
| `FR-<COMP>-NN` | RFP §기능 요구 | SRS가 **같은 번호로** 정련, PRD가 Then에 인용 | 기능 요구 — 무엇을 하는가 |
| `NFR-<COMP>-NN` | RFP §품질 요구 | SRS가 **같은 번호로** 정련하고 합격값을 소유 | 품질 요구 — 얼마나 잘 하는가 (성능·신뢰성·보안·사용성·유지보수성) |
| `TC-<COMP>-NN` | TC 문서 | 테스트 함수에 태깅 | 시험 케이스 |

- 다음 빈 번호부터 이어 붙인다. 재배치·재사용 절대 금지.
- 폐기는 행 삭제가 아니라 취소선 + 대체 포인터:
  `~~FR-SEARCH-03~~ **[폐기 — FR-SEARCH-07로 대체]**`
- SRS는 새 FR·NFR 번호를 만들지 않는다. 새 요구가 필요하면 RFP에 먼저 추가한다.
- **요구 ID 가족은 이 셋뿐이다.** `AT`·`PR`·`AR`·`SR` 같은 가족을 임의로 만들지
  않는다. PRD의 `EPIC-NN`·`US-<에픽>-<순번>`은 요구 ID가 아니라 문서 구조 번호이며,
  append-only 규율만 똑같이 적용한다.
- **수치 합격선은 SRS의 비기능 요구 표가 소유한다.** 승인 전 값은 `미승인`으로
  두고 TC는 승인된 값을 인용만 한다. TC에 처음 등장하는 수치는 근거가 없다.
- 추적성 표에는 공식 ID만 쓴다. 피드백 번호·회의 메모 번호는 넣지 않는다.
- 문서 층의 ID 규율은 [README.md](README.md) §2가 권위다.

### 4.2 우선순위와 검증 유형 어휘

| RFP/SRS | PRD | 의미 |
|---|---|---|
| M | P0 | 이번에 반드시 포함 |
| S | P1 | 목표하되 제약 시 조정 가능 |
| C | P2 | 후속 또는 선택 |

검증 유형 4종(SRS·TC 공용): **시험(Test)** 자동/수동 실행 · **검사(Inspection)**
문서·표시 검토 · **시연(Demonstration)** 사용자 시나리오 · **분석(Analysis)** 계산·추론.
모든 요구는 이 중 하나로 확인 가능해야 한다. 확인 방법이 없는 문장은 요구가 아니다.

### 4.3 문서 헤더·상태·미결 사항 (전 문서 공통)

문서 층의 공통 골격은 [README.md](README.md) §3이 권위다. 요약하면:

- 헤더 표: 문서 역할 · 버전 · 기준 문서(상위 문서 버전 링크) · 상태.
- 상태는 `Draft → Review → Baseline`으로만 승격한다. 개발 중에는 Draft를 유지하고,
  새 문서로 대체된 문서는 `Superseded`로 표시해 보존한다.
- 변경 이력 표: `| 버전 | 날짜 | 변경 요약 | 영향 범위 |` — 오탈자 수정과 요구
  변경을 구분한다.
- 미결 사항 표: `| ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |` — 본문의 모든
  `[확인 필요]`를 여기 모은다. 결정된 항목은 지우지 말고 `Decided`로 바꾸고
  반영 위치를 연결한다.
- 용어는 프로젝트 용어집(SRS §용어)에서 확정하고 전 문서에서 같은 뜻으로만 쓴다.

### 4.4 요구와 구현 상태의 분리

요구 문서(MRD·RFP·PRD·SRS)에서 `구현됨`, `현재 미구현`, `지원 예정`, 특정 파일
경로, 내부 함수명을 **제거**한다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 키워드 검색 기능이 **구현되었다**. | 시스템은 입력 키워드와 일치하는 결과를 관련도 순으로 **반환해야 한다**. |

역할 분담은 세 줄이다:

```
요구 문서:      무엇을 보장해야 하는가
TC 리포트:      무엇이 검증되었는가
git 이력:       언제 구현되었는가
```

## 5. 에이전트 컨텍스트 층 — CLAUDE.md와 SKILL.md

AI 에이전트는 매 세션 기억이 리셋된다. "프로젝트를 처음 만나는 유능한 신입에게
30분 만에 브리핑하는 문서"를 저장소에 상주시켜, 체인의 규율을 에이전트가 매 세션
자동으로 읽게 만든다. **이 층이 체인의 실행 장치다.**

### 5.1 CLAUDE.md — 항상 로드되는 지도 (200줄 안팎)

| # | 섹션 | 내용 |
|---|---|---|
| 1 | 프로젝트 개요 | 한 문단 + 기술 스택 |
| 2 | 디렉토리 구조 | **파일마다 역할·함정을 한 줄 주석으로 단 트리** |
| 3 | 아키텍처 원칙(불변식) | 절대 어기면 안 되는 규칙 3~5개, 최우선 준수 |
| 4 | 코딩 규칙 | 리뷰에서 반복 지적하던 것. 부정 규칙("~하지 마라") 포함 |
| 5 | API·계약 표 | 시스템 계약 표면의 단일 목록 |
| 6 | 개발 명령어 | 복붙 가능한 셸 블록 |
| 7 | 정책·결정 로그 | 결정된 동작 + 이유 + **반증된 대안** + 근거 문서 링크 |
| 8 | 보안 규칙 | 커밋 금지 대상, 비밀 관리 |
| 9 | 문서-코드 동기화 규칙 | §7.1의 트리거 표 — **체인 강제 지점** |

- 정책 로그가 가장 가치 있는 섹션이다. "왜 이렇게 되어 있는가"를 반증된 대안과
  함께 적어야, 나중에 다른 에이전트가 의도된 동작을 버그로 오인해 되돌리는
  사고를 막는다.
- 수치는 근거와 함께 적는다. "성능 개선"이 아니라 "38ms→8ms(실측, report 링크)".
- 코드를 복사하지 않는다. 컨텍스트는 코드의 위치와 주의 지점을 가리키는 안내다.

### 5.2 SKILL.md — 필요할 때만 로드되는 전문 지식 (영역당 100줄 안팎)

파일 위치는 `.claude/skills/<이름>/SKILL.md`. 이름은 디렉토리명과 일치시킨다.

프론트매터는 3개 키만 쓴다:

```yaml
---
name: <디렉토리명과 동일>
description: "<프로젝트 약칭+영역 한 줄>. Use when: <트리거 키워드 나열>. Covers: <담당 파일 glob·경로>."
argument-hint: "대상 (예: a, b)"
---
```

**description이 자동 로드의 전부다.** `Use when:`에는 네 종류를 섞어 넣는다 —
① 도메인 용어 ② 기술 용어 ③ 코드 식별자(설정 키·파일명) ④ **증상·에러**
("~가 깨질 때", "~오류"). ④가 가장 자주 빠지는데, 사용자는 기능 이름이 아니라
고장 난 현상으로 말을 건다. 권장 길이 220~450자.

본문 골격: `흐름/핵심 파일 표` → `도메인 섹션(설정 키 표·수치)` →
`주의·함정(실제로 겪은 사례만)` → `관련 문서(SDLC 경로)`. 구현 코드는 넣지
않는다 — 시그니처·설정 키·측정 수치·함정만.

운영 규칙:

- 스킬은 코드가 커지고 영역 지식이 쌓일 때 추가한다(초기엔 CLAUDE.md만).
  3~7개가 적정이며, 스킬끼리 서로 참조하지 않고 `Covers:`로 영역을 나눈다.
- 모든 스킬 마지막 줄은 CLAUDE.md 정합을 가리킨다("설정 키 변경 시 CLAUDE.md
  정책 메모도 함께 갱신").
- 다른 도구용 미러(`AGENTS.md` 등)는 만들지 않거나, 만들면 git에 커밋하고
  원본과 같은 커밋으로 움직인다. **낡은 미러는 없는 것보다 나쁘다.**

## 6. 검증 자동화 층 — TC 태깅과 자동 대조

체인에서 기계가 감시하는 유일한 연결이다. 파일 3개 + CI 워크플로 1개, 외부
의존성 0으로 구축한다. 골자는 부록 A.

**아래 구현은 Python/pytest 기준이다.** 다른 언어면 도구만 바꾸고 계약 세 줄은
그대로 지킨다 — ① 테스트에 TC-ID를 태깅한다 ② 실행 산출물에 그 ID가 **기계
판독 가능하게** 남는다 ③ 리포트가 TC 문서와 집합 비교해 orphan·미커버를 낸다.

| 파일 | 계약 | 함정 |
|---|---|---|
| `pytest.ini` | `tc` 마커 등록 + **`junit_family = legacy`** | legacy가 없으면 태그가 XML에 남지 않아 **집계가 전부 비게 된다**. 이식 시 최우선 확인 |
| `conftest.py` | autouse 픽스처가 `@pytest.mark.tc(...)` 인자들을 JUnit property로 기록 | 한 테스트가 여러 TC를 검증하면 **한 데코레이터에 인자를 나열**한다. 데코레이터를 겹치면 하나만 인식되어 나머지가 누락된다 |
| `generate_report.py` | pytest 실행 → JUnit 집계 → `docs/tc/TC_*.md` 정규식 대조 → 리포트. 종료코드가 CI 게이트 | TC 문서에 구조를 강요하지 말 것(정규식 `TC-([A-Z]+)-(\d+)`로만 훑는다). 한 TC 문서에 여러 테스트 파일이 걸리면 **전 파일 합산**으로 집계할 것 |
| CI 워크플로 | pytest가 아니라 **리포트 생성기를** 호출하고 리포트를 아티팩트로 남긴다 | `if: always()`로 실패 시에도 리포트 업로드 |

두 지표 — 단순 집합 차집합이다:

| 지표 | 정의 | 의미 | 게이트 |
|---|---|---|---|
| **orphan** | 태그됨 − 문서 정의 | 문서에 없는 TC를 테스트가 주장 = 오타 또는 드리프트 | **커밋 전 0** |
| **미커버** | 문서 정의 − 태그됨 | 테스트 없는 TC = 미구현이거나 수동·시연 유형 | 사람 판단(게이트 아님) |

테스트 작성 컨벤션:

```python
@pytest.mark.tc("TC-SEARCH-01")                       # ① 기계용 태깅
def test_search_rank_tc_search_01(client):            # ② grep·가독성용
    """TC-SEARCH-01 / FR-SEARCH-01: 키워드 일치 결과가 관련도 순으로 반환된다."""  # ③ 사람용
```

- 테스트 파일 헤더 docstring에 **"여기서 안 다루는 것"**을 명시한다 — 미커버
  숫자가 변명이 아니라 범위 선언이 된다.
- 무거운 의존(모델·외부 API)은 stub으로 대체하되, stub은 실제 구현의 **출력
  계약**을 그대로 흉내낸다. 테스트가 깨지면 stub을 실제 계약에 맞추지,
  테스트를 약화시키지 않는다.
- **가벼운 CI 레인**: CI에는 핵심 의존만 설치하고 무거운 패키지(모델 프레임워크
  등)는 아예 넣지 않는다. 제품 코드는 무거운 import를 함수 안으로 지연시킨다 —
  설치 목록 자체가 "가볍게 유지하라"는 강제 장치가 되고, PR마다 수십 초 안에
  전체 계약 테스트가 돈다. 무거운 정확도 검증은 별도 벤치마크로 분리한다.
- 내부 구현 회귀(캐시·락·리팩터 보호)에는 TC 번호를 발급하지 않는다. TC가
  "제품이 지킬 약속"이 아니라 "테스트 존재 증명"으로 변질되는 것을 막는다.
  이 구분이 필요해질 만큼 테스트가 늘면 §9의 레인 분리로 승급한다.

판정 규칙: 스킵은 통과가 아니다 · 실행 안 한 시험은 통과가 아니다 · 테스트
삭제·skip·assertion 완화로 실패를 숨기지 않는다 · 문서 정합 완료와 검증 완료는
다른 상태다.

## 7. 일상 운영 루프 — 역반영과 커밋

### 7.1 코드 → 문서 트리거 표 (CLAUDE.md §9에 넣어 에이전트가 매 세션 읽게 한다)

| 코드 변경 | 같은 커밋에 갱신할 대상 |
|---|---|
| 새 API·엔드포인트 | CLAUDE.md API 표 + RFP·PRD·SRS·TC |
| 동작·정책 변경 | 해당 FR·NFR/TC + 추적성 표 |
| 새 모듈·디렉토리 | CLAUDE.md 디렉토리 구조 |
| 설정 키 추가·변경 | CLAUDE.md 정책 메모 + 관련 SKILL 설정 표 |
| 새 테스트 파일 | 리포트 생성기 등록 + TC 태깅 + TC 문서 |

### 7.2 역반영 6단계

개발 중 코드의 동작이 바뀌는 것은 막을 수 없다. 대신 같은 커밋 안에서 문서를
따라 바꾼다. **'역'은 코드에서 문서로 거슬러 반영한다는 뜻이고, 문서 사이에서는
영향이 닿는 가장 상위 문서부터 아래로 내려간다.** (요구 자체가 새로 생기면
RFP부터, 보장 수준만 달라지면 SRS부터.)

1. **번호 잇기** — 다음 빈 FR·NFR·TC 번호. 재사용 금지
2. **RFP** — 요구 정의(M/S/C). 구현값(경로·임계값) 인용 금지
3. **PRD** — 스토리·수용 기준으로 전개
4. **SRS** — 같은 FR·NFR 번호를 검증 가능 문구 + 검증 유형으로 정련.
   품질 요구면 측정 대상·관찰 지점·합격값·승인 상태까지 채운다
5. **TC** — 전제·절차·기대·Pass/Fail 전개
6. **추적성 표 동시 정합** — RFP·SRS·TC의 표가 서로 어긋나지 않게

마무리 확인 — 아래가 실패 0 · **orphan 0**일 때만 커밋한다.

```bash
python -m pytest test -q && python test/generate_report.py
```

### 7.3 커밋 규약

```
<type>(<scope>): <무엇을 어떻게 했는가 한 줄>

<왜 문제였고 어떻게 고쳤는가>

<추가한 TC 번호>와 <역반영한 문서 목록>.

검증: 전체 테스트 N passed; orphan 0.
```

- type: feat / fix / refactor / test / docs
- 플레이키(간헐 실패) 의심이 있으면 전체 테스트를 연속 2회 돌려
  "연속 2회 각 N passed"로 남긴다
- 코드·테스트·문서·컨텍스트가 **한 커밋에 함께** 담긴 diff가 방법론이 살아
  있다는 증거다. 코드만 있는 커밋이 반복되면 이미 무너지고 있는 것이다.

### 7.4 근거 문서 계층 — docs/report/ 와 docs/research/

요구 문서와 별개로 "왜 이 수치·이 구조인가"를 답하는 계층이다. 새 매직넘버·
임계값·모델 선택에는 반드시 여기 보고서 링크가 붙는다.

보고서 헤더 규약: **측정 대상 코드(커밋 SHA) 명시** · 새로 측정한 것과
재사용한 과거 실측 구분 · 결론 한 줄 · **반증된 대안 기록**("~는 이 환경에서
답이 아니다(+3%, 실측)") — 반증 기록이 6개월 뒤 같은 아이디어의 재실험 비용을
0으로 만든다.

## 8. 최종 baseline 정합

개발 중과 최종 정합은 정책이 다르다.

| | 개발 중 | 최종 정합 |
|---|---|---|
| 원칙 | 코드 변경과 문서를 같은 커밋에 | 현재 구현을 **무조건 복사하지 않는다** |
| 이유 | 미루면 영원히 안 함 | 임시 구현이 요구로 굳는 것을 방지 |
| 상태 | Draft 유지 | Baseline으로 승격 |

최종 정합은 기능 안정화 후 **상위 문서 → 하위 문서 순으로 한 번에** 진행한다:
제품 범위·유지할 설계 결정 확정 → MRD → RFP → PRD → SRS(원자화·모호 표현 제거)
→ SDD 재작성 → TC 정합(리포트로 orphan·미커버·중복 확인) → 필요 시 운영 문서.
원칙은 "구현되어 있다"가 아니라 "무엇을 보장해야 하는가"로 다시 쓰는 것이다.

## 9. 도입 순서와 확장 신호

**Week 1 — 기준 모델 만들기(가장 중요).** 핵심 컴포넌트 하나를 골라 체인을
끝까지 완주한다: RFP에 FR 5~15개·NFR 3~7개 → PRD 스토리 3~8개 → SRS 정련 →
SDD ADR 3~8개 → TC 10~20개 →
(이 숫자는 체인을 처음 완주할 때 참고하는 **도입 안내**이지 판정 기준이
아니다. 개별 문서의 합격 기준으로 쓰지 않는다.)
태깅된 테스트 3~5개 → 리포트 orphan 0. 이 세트가 이후 모든 문서의 복사 원본이
된다.

**정착 습관 3개** — ① `git show --stat`에 docs/가 보이는가 ② 커밋 메시지에
"orphan 0"이 적혀 있는가 ③ 새 매직넘버에 근거 문서 링크가 있는가.

**확장은 신호가 올 때만 한다:**

| 확장 | 신호 |
|---|---|
| 문서 분할(마스터/컴포넌트) | 컴포넌트가 늘어 문서 하나가 비대해질 때 |
| 스킬 분리 | 코드가 커지고 영역별 지식이 쌓일 때 (5천 줄 미만이면 불필요) |
| 테스트 레인 분리(인수/내부/도구) | TC 하나에 테스트 수십 개가 매달리고, 내부 회귀까지 TC 번호를 요구받을 때 |
| TC 문서를 권위로 승격 | 자동 테스트로 표현할 수 없는 검증(수동 시연·평가·법무 검토)이 인수 조건에 들어올 때 — 이때부터 리포트는 "특정 실행의 증거"로 강등되고, 인수 판정은 TC 문서가 소유한다 |

승급은 목표가 아니라 신호 대응이다. 신호가 없으면 최소 코어로 끝까지 가는 것이
정상이다.

**도입 저항에 대한 답** — "문서 쓸 시간에 코드를": 문서가 에이전트 컨텍스트이자
리뷰 근거다. 없으면 같은 설명을 매 세션 반복한다 · "요구가 계속 바뀌는데":
그래서 append-only다. 바뀌는 것을 기록하는 체계지 고정하는 체계가 아니다 ·
"태깅이 번거롭다": 데코레이터 한 줄로 "이 코드가 어떤 요구를 지키나"에 번호로
답하게 된다.

## 11. 알려진 한계와 완화

| 한계 | 완화 |
|---|---|
| 문서 작성 비용은 실재한다 — 한 줄 수정에 풀 체인은 낭비 | 최소 코어로 시작하고 변경 크기에 비례해 적용한다 |
| 명세도 낡는다 | 동기화 커밋과 자동 대조가 이에 대한 대응이다. 이 둘 없이 문서만 만들지 않는다 |
| 탐색·실험 단계에는 맞지 않는다 | 실험은 가볍게 하고, 살아남은 것만 체인에 편입한다 |
| 추적성 표의 상호 일치는 기계가 검사하지 않는다 | TC 대조만 자동이다. 나머지는 커밋 전 체크리스트로 지킨다 |
| SDD가 가장 뒤처지기 쉽다 | 설계 결정 기록(ADR) 표 하나로만 시작한다 |
| orphan이 기본으로는 빌드를 깨지 않는다 | 리포트 생성기에서 orphan 시 종료코드 1을 반환하게 한 줄 하드닝한다 |

## 부록 A. 장치 복사용 골자

아래는 **Python/pytest 기준 구현**이다. 다른 언어면 §6의 계약 세 줄만 지키고
도구는 그 언어의 것으로 바꾼다.

`test/pytest.ini`

```ini
[pytest]
pythonpath = <소스 루트>
testpaths = test
junit_family = legacy
markers =
    tc(id): 이 테스트가 검증하는 TC 문서 ID (예: tc("TC-SEARCH-01"))
```

`test/conftest.py`

```python
import pytest

@pytest.fixture(autouse=True)
def _record_tc(request, record_property):
    """@pytest.mark.tc("TC-...") → JUnit <property name="tc">.
    리포트 생성기가 이 property를 읽어 TC 단위로 pass/fail을 집계한다."""
    marker = request.node.get_closest_marker("tc")
    if marker:
        for tc_id in marker.args:
            record_property("tc", str(tc_id))
```

`test/generate_report.py` — 구현 계약(함수 내부는 프로젝트가 채운다):

```python

# 3) docs/tc/TC_*.md를 정규식 TC-([A-Z]+)-(\d+) 로 훑어 "문서가 정의한 ID 집합"을 만든다
```

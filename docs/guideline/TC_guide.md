# TC 작성 가이드 (TC_guide)

> TC(Test Case, 시험 기준서)는 **"요구가 충족되었음을 어떻게 증명하는가"**에
> 답한다. 체인의 종점이자 문서가 코드와 만나는 유일한 지점이다 — 여기서 태어난
> `TC-<COMP>-NN`이 테스트 코드에 태깅되고, 리포트가 문서와 태그를 자동 대조한다.
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 확정된 SRS (모든 TC는 SRS의 FR·NFR을 검증하기 위해 존재한다)
- **출력**: `TC-<COMP>-NN` 시험 케이스(전제·절차·기대 결과·Pass/Fail 기준),
  실행 순서, 요구↔TC↔테스트 코드 추적표
- **코드 연결**: 테스트 함수에 TC-ID를 태깅하고, **테스트 실행 산출물(JUnit XML
  등)에 그 ID가 기계 판독 가능하게 남아야 한다.** 리포트 생성기가 문서와 태그를
  집합 비교하므로, 이 조건이 충족되지 않으면 대조 결과가 오류 표시 없이 비게 된다.
  - Python: `@pytest.mark.tc("TC-<COMP>-NN")`
  - 다른 언어: 리포트가 읽을 수 있는 태그·메타데이터면 된다
    (예: 테스트 제목에 `[TC-<COMP>-NN]` 삽입)
  커밋 전 orphan(문서에 없는 태그) 0이 게이트다

## 2. 작성 전 준비 (필수)

1. SRS의 FR·NFR 목록과 각각의 **검증 유형**을 뽑는다. 시험(Test) 유형만 자동
   테스트 대상이고, 검사·시연·분석 유형은 TC에 절차만 정의하고 자동화 대상에서
   구분한다. SRS가 적어 둔 "왜 시험으로 만들 수 없는가"를 그대로 옮겨 적는다.
2. **NFR의 합격값 상태를 확인한다** — SRS §3 비기능 요구 표의 `승인 상태`를 본다.
   - `승인` → 그 합격값을 **그대로 인용해** Pass/Fail 기준에 쓴다.
   - `미승인` → 절차와 측정 지점까지만 정의하고 Pass/Fail 기준에는
     `합격값 승인 후 확정`이라고 적은 뒤 자동화 대상에서 분리한다.
   **TC에 처음 등장하는 수치는 근거 없는 합격선이다.** 합격값은 SRS가 소유한다.
3. 각 요구에 대해 정상 경로 외에 **실패·경계·복구** 시나리오를 목록화한다.
   버그는 대부분 정상 경로 밖에서 나온다.
4. **TC 수는 SRS가 정한다** — 시험 유형 요구마다 최소 하나, 거기에 실패·경계·
   복구 경로가 더해진다. 자동 테스트는 처음부터 전부 만들지 말고 핵심 경로부터
   태깅해 나간다.

## 3. 문서 골격

```
헤더 표: 문서 역할 · 버전 · SRS 기준(버전 링크) · 테스트 코드 위치 · 상태(Draft)
## 1. 시험 전략           시험 수준(단위/API/수동), 자동화 범위와 그 밖의 범위
## 2. 환경과 전제         표: 구분|전제 (실행 환경, 데이터, 계정 등)
## 3. 시험 케이스         SRS §2 그룹과 1:1 구성. 그룹 제목에 FR 범위 병기
   | TC ID | 검증 FR·NFR | 전제 | 절차 | 기대 결과 | Pass/Fail 기준 |
   절차는 ① ② ③ 번호로, Pass/Fail은 "A **그리고** B이면 Pass, 아니면 Fail"의
   불리언 조합으로
## 4. 실행 순서           그룹 간 의존이 있으면 순서를 명시
## 5. 판정 규칙           이 가이드 §5의 규칙을 그대로 옮겨 적는다
## 6. 추적성              표 위에 체인 한 줄:
   `MRD → RFP → PRD → SRS → **TC** → test (기계가 대조하는 유일한 연결)`
   | SRS FR·NFR | TC ID | 테스트 함수(파일::함수명) |
   표 아래에 **검수 합계 한 줄**을 남긴다(§7에서 센 숫자)
## 7. 변경 이력           | 버전 | 날짜 | 변경 요약 | 영향 TC |
## 8. 미결 사항           | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
```

## 4. 작성 규칙

- **TC 하나 = 실패 원인 하나.** 여러 가지를 한 번에 확인하면 실패했을 때
  무엇이 깨졌는지 알 수 없다.
- **정상 경로만 쓰지 않는다.** 실패 입력, 경계값, 권한 거부, 빈 결과, 부분
  실패, 복구를 반드시 포함한다.
- **모든 TC에 검증 요구(FR 또는 NFR)를 단다.** 요구 없는 TC는 "테스트가
  존재한다"는 증명일 뿐 "요구가 지켜졌다"는 증명이 아니다.
- **합격 기준은 실행 전에 잠근다.** 결과를 보고 기준을 조정하면 시험이 아니라
  결과에 대한 사후 정당화가 된다.
- **수치 합격선은 SRS §3에서 인용한다.** TC는 그 값을 옮겨 적을 뿐 새로 정하지
  않는다. 인용한 값의 출처(요구 ID)를 Pass/Fail 기준에 함께 남긴다.
- **태깅 규약**: 한 테스트 함수가 여러 TC를 검증하면 데코레이터 하나에 인자를
  나열한다 — `@pytest.mark.tc("TC-A-01", "TC-A-02")`. 데코레이터를 겹쳐 쓰지
  않는다(하나만 인식되어 나머지가 누락된다).
- 내부 구현 회귀(캐시·락·리팩터 보호용 테스트)에는 TC 번호를 발급하지 않는다.
  TC는 제품이 지킬 약속이지 테스트 존재 증명이 아니다.

### TC 예시

앞 문서의 `FR-LIB-01`·`FR-LIB-02`·`NFR-LIB-01`을 검증하는 시험이다.

| TC ID | 검증 FR | 전제 | 절차 | 기대 결과 | Pass/Fail 기준 |
|---|---|---|---|---|---|
| TC-LIB-01 | FR-LIB-01 | 제목에 "어린"이 든 도서 1건, 들지 않은 도서 2건이 등록돼 있다 | ① "어린"으로 검색 ② 결과 목록 확인 | 대상 1건만 결과에 나온다 | 대상 도서가 결과에 있고 **그리고** 나머지 2건이 0건이면 Pass |
| TC-LIB-02 | FR-LIB-02 | 검색어와 일치하는 도서가 장서에 없다 | ① 그 검색어로 검색 ② 화면 문구 확인 | 결과 없음이 표시되고 장서 부재를 단정하지 않는다 | 결과가 0건이고 **그리고** 단정 문구("장서에 없습니다" 류)가 0건이면 Pass |
| TC-LIB-03 | NFR-LIB-01 | 장서 1,000건이 등록돼 있다 | ① 검색 요청 ② 응답까지 경과 시간 측정 | 경과 시간이 기록된다 | **합격값 승인 후 확정** — SRS §3의 승인 상태가 `미승인`이므로 자동화 대상에서 분리 |

`TC-LIB-02`는 MRD의 원칙("찾지 못한 것과 없는 것을 구분한다")에서 출발해
`FR-LIB-02`로 확정된 요구를 검증한다. **하나의 문제 인식이 여섯 문서를 거쳐
실행 가능한 판정으로 귀결되는 것**이 이 체인의 목적이다(README §1 관통 표).

**부적합한 TC**

| ✗ | 문제점 |
|---|---|
| Pass/Fail이 "정상 동작하면 Pass" | 무엇을 세어 무엇과 비교하는지가 없다 |
| 한 TC가 검색·정렬·대출 상태를 한 번에 확인 | 실패했을 때 무엇이 깨졌는지 모른다 |
| 검증 요구 칸이 비어 있다 | 요구와 연결되지 않은 시험은 증거가 아니다 |

## 5. 판정 규칙 (문서에 그대로 포함할 것)

실행 결과는 `PASS` · `FAIL` · `SKIPPED` · `BLOCKED`(전제 미충족) · `NOT_RUN`
다섯 중 하나로 적는다. **`PASS`가 아닌 것은 전부 통과가 아니다.**

1. 스킵(skip)은 통과가 아니다.
2. 실행하지 않은 시험은 통과가 아니다.
3. 정적 검사·stub 시험은 실제 실행 환경 검증을 대체하지 않는다.
4. 테스트 삭제·skip 처리·assertion 완화로 실패를 숨기지 않는다.
5. 같은 요구를 여러 테스트가 검증해도 통과 개수로 충족을 부풀리지 않는다.
6. 문서에 없는 TC 태그(orphan)는 오타 또는 드리프트다 — 커밋 전 0이어야 한다.
7. 테스트 없는 TC(미커버)는 실패가 아니라 "자동화 미연결"이며, 수동·시연
   유형인지 미구현인지 구분해 표시한다.

## 6. 금지 사항

- FR 연계 없는 TC, SRS에 없는 요구를 검증하는 TC(요구가 필요하면 SRS·RFP부터)
- 해석의 여지가 있는 판정 기준("적절히 동작하면", "충분히 빠르면")
- 실행 전 합격선의 사후 변경
- 제품 배경·설계 이유의 반복 서술(상위 문서 참조로 대체)

## 7. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] SRS의 모든 시험(Test) 유형 FR·NFR에 최소 1개의 TC가 있다
      → 센 결과를 골격 §6 합계 줄에 적는다:
        `시험 유형 요구 __개 / TC가 붙은 요구 __개 / 미커버 __개`
- [ ] 모든 TC가 `TC-<COMP>-NN` 형식이고 검증 요구가 달려 있다
      (검증 요구 칸이 빈 행 0개, 번호에 빠짐·중복 0)
- [ ] 모든 Pass/Fail 기준이 불리언 조합으로 해석 여지가 없다
      ("정상"·"적절히"·"충분히"·"잘"을 검색해 0건인지 확인)
- [ ] 한 TC가 한 가지만 확인한다
      (기대 결과 칸에서 "그리고"로 이어진 **서로 다른 기능**이 있으면 쪼갠다)
- [ ] 실패·경계·복구 경로가 포함됐다
      (실패 입력 · 경계값 · 빈 결과 · 권한 거부 · 복구를 각각 검증하는 TC가
      있는지 다섯 가지를 하나씩 확인)
- [ ] TC에 새로 등장한 수치가 없다
      (수치가 있는 Pass/Fail 기준마다 출처 요구 ID가 붙어 있는지 확인)
- [ ] 검사·시연 유형 요구가 자동화 대상과 구분되어 있고 그 이유가 적혀 있다
- [ ] 추적표의 테스트 함수 경로가 실제 태깅과 일치한다 (orphan 0)

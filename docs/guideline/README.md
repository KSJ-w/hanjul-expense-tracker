# 문서 작성 가이드 공통 규칙

> 이 폴더의 `*_guide.md`는 AI 에이전트에게 주는 문서 작성 지침이다.
> 각 파일은 "이 문서는 이렇게 조사하고 이렇게 작성한다"를 정의하며,
> 실습에서는 해당 가이드 파일과 상위 문서를 AI에게 주고 초안 작성을 맡긴다.

## 1. 전체 흐름

```text
GOAL.md (사람이 작성 — 만들고 싶은 것을 자유롭게. 형식·분량·항목 제한 없음)
   ↓
MRD  →  RFP  →  PRD  →  SRS  →  TC  →  테스트 코드(@pytest.mark.tc)
                          └→ SDD (곁가지 — 설계와 결정 기록)
```

- GOAL은 체인 밖 입력물이다. **주제를 정해 줄 뿐 MRD 내용의 근거가 아니며**,
  MRD가 완성되면 역할이 끝난다. MRD가 사실로 적는 것은 조사에서 나온다.
- 각 문서는 자기 질문 하나에만 답한다. 애매한 내용은 MRD→RFP→PRD→SRS→SDD→TC
  순서로 대조해 처음 해당하는 문서에 적는다.
- 상위 문서가 확정되기 전에 하위 문서를 시작하지 않는다.
- `.claude/CLAUDE.md`는 이 체인 **밖의 컨텍스트 층**이다. 요구 번호가 흐르지
  않고 진실의 원천이 합의가 아니라 코드이며, 작성법은
  [CLAUDE_guide.md](CLAUDE_guide.md)가 소유한다.

| 문서 | 답하는 질문 | 만들어 내는 것 |
|---|---|---|
| MRD | 왜 만드는가 | 문제 정의, 범위 방향, 성공 질문 |
| RFP | 이번 개발에서 무엇을 요구하는가 | 범위 확정, **FR·NFR 번호 탄생** |
| PRD | 사용자가 어떤 경험을 얻는가 | 사용자 스토리, 수용 조건 |
| SRS | 무엇을 얼마나 정확히 보장하는가 | 검증 가능한 요구(FR·NFR 번호 유지), 검증 유형 |
| SDD | 어떻게 구현하는가 | 구조, 설계 결정 기록 |
| TC | 요구 충족을 어떻게 증명하는가 | **TC 번호 탄생**, 절차·합격 기준 |

### 한 요구가 문서 여섯 개를 통과하는 모습

같은 내용이 층마다 어떤 언어로 바뀌는지 보여 주는 표준 예제다. 각 가이드의 예시는
이 표의 해당 칸을 상세히 전개한 것이다.

| 문서 | 같은 요구, 다른 언어 |
|---|---|
| MRD | 이용자는 검색 결과가 비면 장서에 없다고 오해하고 탐색을 포기한다 → 원칙: **찾지 못한 것과 없는 것을 구분한다** |
| RFP | `FR-LIB-02` 시스템은 검색 결과가 없을 때 해당 도서가 장서에 없다는 뜻으로 표시해서는 안 된다 \| M |
| PRD | **Given** 일치하는 도서가 없을 때 **When** 검색하면 **Then** 결과 없음으로 표시하되 장서에 없다고 단정해서는 안 된다 `(FR-LIB-02)` |
| SRS | `FR-LIB-02` 시스템은 결과가 0건일 때 장서 부재를 단정하는 문구를 표시해서는 안 된다 \| M \| 시험 |
| SDD | 조회 결과 0건과 조회 실패를 서로 다른 응답으로 구분한다 `(ADR-002)` |
| TC | `TC-LIB-02` 결과가 0건이고 **그리고** 단정 문구가 0건이면 Pass |

여섯 줄이 모두 채워지지 않으면 해당 층이 불필요하거나 요구가 아직 충분히
정의되지 않은 것이다.

## 2. ID 규율 (전 문서 공통)

이 절의 규율을 지키지 않으면 문서 사이의 추적성이 성립하지 않는다.

- 기능 요구 ID는 `FR-<COMP>-NN` 형식이다. `<COMP>`는 컴포넌트 약칭(영대문자,
  예: SEARCH), `NN`은 01부터의 순번. **RFP에서 부여되어 SRS까지 같은 번호로 유지**된다.
  SRS는 새 번호를 만들지 않고 같은 번호의 문구를 검증 가능하게 다듬는다.
- 품질(비기능) 요구 ID는 `NFR-<COMP>-NN` 형식이다. FR이 "무엇을 하는가"라면
  NFR은 "얼마나 잘 하는가"(성능·신뢰성·보안·사용성·유지보수성)를 요구한다.
  FR과 마찬가지로 **RFP에서 부여되어 SRS까지 같은 번호로 유지**된다.
- 시험 ID는 `TC-<COMP>-NN` 형식이며 TC 문서에서 부여되어 테스트 코드에 태깅된다.
- **요구 ID 가족은 이 셋뿐이다.** `FR`·`NFR`·`TC` 밖의 요구 가족(PR·AR·SR 등)을
  임의로 만들지 않는다. 요구 종류가 더 필요해 보이면 만들지 말고 미결 사항에
  질문으로 남긴다.
- PRD의 `EPIC-NN`·`US-<에픽>-<순번>`은 **요구 ID가 아니라 문서 구조 번호**다.
  요구는 어디까지나 그 스토리가 인용하는 FR·NFR이며, 구조 번호에도
  append-only 규율은 똑같이 적용한다.
- **append-only**: 한 번 부여한 번호는 재사용·재배치하지 않는다. 새 요구는 다음 빈
  번호부터 이어 붙인다. 폐기할 때는 행을 지우지 않고 취소선과 대체 포인터를 남긴다.
  (예: `~~FR-SEARCH-03~~ [폐기 — FR-SEARCH-07로 대체]`)
- 추적성 표에는 공식 ID만 쓴다. 회의 메모 번호, 피드백 번호 같은 비공식 식별자를
  넣지 않는다.

## 3. 문서 공통 골격 (전 문서 공통)

개별 가이드의 골격에 적혀 있지 않더라도 모든 문서가 아래 셋을 포함한다.

- **헤더 표** — 문서 역할 · 버전 · 상위 문서 기준(버전 링크) · 상태.
  상태는 `Draft → Review → Baseline` 순으로만 승격한다. 개발 중에는 Draft를
  유지하고, 새 문서로 대체된 문서는 `Superseded`로 표시해 보존한다.
- **변경 이력 표** — `| 버전 | 날짜 | 변경 요약 | 영향 범위 |`.
  오탈자 수정과 요구·방향 변경을 구분해 적는다.
- **미결 사항 표** — `| ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |`.
  본문의 모든 `[확인 필요]`와 사람에게 물어야 할 것을 여기 모은다. 결정된
  항목은 지우지 말고 `Decided`로 바꾸고 반영 위치를 연결한다.

용어는 SRS의 용어집에서 확정하고, 전 문서에서 같은 용어를 같은 뜻으로만 쓴다.

**예외** — `CLAUDE.md`는 요구 문서가 아니라 컨텍스트 층이므로 이 절을 적용하지
않는다. 상태·변경 이력은 git이 소유하고, 미결 사항은 요구 문서에 남긴다.

## 4. 근거와 수치 (전 문서 공통)

- 모든 수치·통계·주장에는 출처를 붙인다. 외부 자료는 각주와 링크, 내부 측정은
  측정 기록 위치를 적는다.
- 출처를 확보하지 못한 수치는 쓰지 않는다. 필요하면 승인 상태를 `미승인`으로
  적어 구분하고 합격선으로 사용하지 않는다(SRS_guide §3의 비기능 요구 표).
- 측정하지 않은 값을 현재 성능처럼 서술하지 않는다.

## 5. 비주장 원칙 (전 문서 공통)

- 요구 문서(MRD·RFP·PRD·SRS)에는 구현 상태를 적지 않는다. "구현됨", "완료",
  "현재 미구현" 같은 표기 금지. 요구는 "무엇을 보장해야 하는가"만 말한다.
- 범위 밖(비범위) 항목은 반드시 명시한다. 비범위는 "만들지 않기로 약속한 것"이지
  실패나 미완성이 아니다.
- 문서 작성 완료와 검증 완료는 다른 상태다. 문서가 완성돼도 검증은 TC와 실행
  결과가 판정한다.

## 6. AI 작성 절차 (모든 가이드 공통)

1. 상위 문서와 이 가이드를 읽고, 가이드의 「작성 전 조사·준비」 절을 먼저 수행한다.
2. 가이드의 골격 순서대로 초안을 작성한다.
3. 가이드 마지막의 체크리스트로 자기 검수를 수행하고, 통과하지 못한 항목을 고친다.
   센 숫자는 **문서의 추적표(또는 미결 사항 표) 아래 합계 줄**에 남긴다 —
   대화에만 적으면 사람 검토 때 사라진다.
4. 확신이 없는 내용은 지어내지 말고 `[확인 필요]`로 표시한 뒤, §3의 미결 사항
   표에 질문으로 올린다.
5. 초안은 어디까지나 초안이다. 사람 검토·수정을 거친 뒤에만 확정(Baseline)된다.

## 7. 가이드를 고칠 때 (이 폴더를 유지하는 규율)

가이드의 규칙 한 줄을 고치면 **같은 편집에서** 아래 넷을 함께 확인한다. 하나라도
빠지면 다음 사람은 규칙과 예시가 어긋난 가이드를 받는다.

| # | 확인할 것 | 놓치면 생기는 일 |
|---|---|---|
| 1 | **골격** — 그 규칙이 요구하는 칸·절이 골격에 있는가 | 체크리스트가 요구하는 것을 적을 자리가 없다 |
| 2 | **예시** — 예시가 새 규칙을 통과하는가, 새 규칙의 시연이 있는가 | AI가 규칙보다 예시를 모방해 그대로 위반한다 |
| 3 | **체크리스트** — 검사 방법이 새 규칙과 맞고, 결과를 적을 자리가 있는가 | 검사했는지 증명할 수 없다 |
| 4 | **다른 가이드** — 같은 개념을 쓰는 파일이 함께 바뀌어야 하는가 | 같은 것이 문서마다 다른 이름·형식이 된다 |

이것은 [spec_guide](spec_guide.md) §7.2의 「역반영 6단계」를 가이드 자신에게 적용한
것이다. 문서 체인이 코드 변경을 따라가듯, 가이드도 규칙 변경을 따라가야 한다.

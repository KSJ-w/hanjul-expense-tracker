# SDD 작성 가이드 (SDD_guide)

> SDD(Software Design Document, 소프트웨어 설계 문서)는 처음으로 **"어떻게
> 구현하는가"**에 답한다. 체인의 곁가지로, 요구 번호가 흐르지 않고 검증(TC)의
> 대상도 아니다. 핵심 가치는 **설계 결정을 이유·기각한 대안과 함께 남기는 것**이다.
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 확정된 SRS (설계는 요구를 실현하는 수단이다). 특히 성능·보안·
  유지보수성 NFR은 대부분 **설계가 실현한다** — 이 문서가 그 요구의 답이다
- **출력**: 시스템 구성, 데이터 모델, 핵심 흐름, 실패 처리, **설계 결정 기록(ADR)**
- **위치**: SRS의 곁가지. TC는 요구(SRS)만 검증하며 설계 자체를 검증하지 않는다

## 2. 시작 규칙

SDD는 체인에서 가장 낡기 쉬운 문서다. 처음부터 전체 장을 채우려 하지 말고
**설계 결정 기록(ADR) 표 하나로 시작**한다. 구조·데이터·흐름 절은 결정이 쌓여
설명이 필요해질 때 추가한다. 빈 절을 만들어 두지 않는다.

ADR 수는 **실제로 내린 결정의 수**다. 적을 결정이 없으면 SDD도 아직 없다 —
절을 만들어 빈칸을 채우는 대신, 결정이 생길 때까지 문서를 만들지 않는다.

## 3. 문서 골격

골격은 두 단계다. **처음에는 아래 최소 골격만 만든다.** §2의 "빈 절을 만들지
않는다"와 충돌하지 않도록, 성장 후 절은 조건이 실제로 생겼을 때만 추가한다.

### 3.1 최소 시작 골격

```
헤더 표: 문서 역할 · 버전 · SRS 기준(버전 링크) · 상태(Draft)
## 1. 목적과 규범 우선순위   이 문서가 소유하는 것(설계·구현 경로)과 충돌 규칙:
                            구조가 실제로 어떤지는 **실행 코드**가,
                            무엇을 보장해야 하는지는 **SRS**가 이긴다.
                            이 문서는 둘 다에 대해 최하위다
## 2. 설계 불변조건          어떤 변경에서도 지켜야 할 구조 규칙(보통 3~7개)
## 3. 설계 결정 기록 (ADR)   이 문서의 핵심 절
   | ID | 날짜 | 결정 | 검토한 대안 | 선택 이유 | 비용·한계 | 되돌릴 조건 | 상태 |
   ADR-001부터 순번. 상태는 `Active` / `Superseded(→ADR-0NN)`.
   결정이 바뀌면 행을 지우지 않고 상태만 바꾸고 새 행을 추가한다
## 4. SRS 추적              | SRS FR·NFR | 실현하는 설계 요소(§ 참조) |
                            체인 한 줄: `SRS → **SDD**(곁가지 · 요구 번호가
                            흐르지 않고 TC의 검증 대상도 아니다)`
## 5. 변경 이력             | 버전 | 날짜 | 변경 요약 | 영향 범위 |
## 6. 미결 사항             | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
```

### 3.2 조건부 추가 절

| 절 | 추가 조건 | 내용 |
|---|---|---|
| 시스템 구성 | 구성 요소가 3개를 넘어 말로 설명이 안 될 때 | 경계 다이어그램(mermaid flowchart) + 배포 단위 표(단위\|책임\|상태 저장 위치) + **의존 방향 규칙**(무엇이 무엇을 참조할 수 있는가) |
| 데이터 모델 | 엔티티가 3개를 넘거나 관계가 헷갈릴 때 | 논리 엔티티 표(entity\|식별·관계\|의미) + 필요시 ER 다이어그램 |
| 핵심 흐름 | 한 요청이 구성 요소 3개 이상을 거칠 때 | 가장 중요한 시나리오 1~2개의 시퀀스(mermaid) |
| 실패와 복구 | 부분 실패가 실제로 일어날 수 있을 때 | 표: 실패\|감지 위치\|격리 범위\|복구\|데이터 영향 |
| 동시성·배포·보안 경계 | 동시 사용자·외부 노출·비밀 관리가 생겼을 때 | SRS의 보안·성능 NFR을 실현하는 구조와 신뢰 경계 |

추가 절은 **§2와 ADR 사이에** 끼워 넣고, ADR·SRS 추적·변경 이력·미결 사항은
항상 마지막 네 절로 유지한다. 절을 추가하면 뒤 절의 번호가 밀리므로 **SRS 추적
표의 `§ 참조`도 같은 편집에서 함께 고친다.** `ADR-001` 같은 결정 ID는 절 번호가
바뀌어도 절대 바뀌지 않는다.

## 4. 작성 규칙

- **코드를 복사하지 않는다.** 함수 본문·클래스 내부를 옮겨 적으면 코드가 바뀌는
  순간 거짓이 된다. 구조·계약·흐름 수준에서 멈추고, 필요하면 파일 경로만
  가리킨다.
- **기각한 대안이 결정만큼 중요하다.** "왜 이걸 안 했는가"가 없으면 6개월 뒤
  누군가 같은 대안을 다시 꺼내 재실험 비용을 치른다.
- **모든 설계 요소는 요구에 연결된다.** "이 구조는 어떤 SRS 요구(FR 또는 NFR)
  때문에 존재하는가"에 답하지 못하는 설계 서술은 근거가 없으므로 삭제한다.
- **결정과 사실을 구분한다.** ADR에는 선택지가 있었고 그중 하나를 선택한 사안만
  기록한다. 선택의 여지가 없던 사항(언어가 이미 정해져 있는 경우 등)은 결정이
  아니라 제약이므로 SRS의 제약과 가정에 둔다.
- **모르는 것을 모른다고 적는다.** 근거를 확인하지 못한 선택은 `근거 미기록`,
  실행으로 검증하지 못한 설계는 `실행 검증 필요`로 표시한다.
- 다이어그램은 mermaid 텍스트로 작성해 문서와 함께 버전 관리되게 한다.

### ADR 예시

앞 문서의 `FR-LIB-01`·`FR-LIB-02`를 실현하는 설계 결정이다.

| ID | 날짜 | 결정 | 검토한 대안 | 선택 이유 | 비용·한계 | 되돌릴 조건 | 상태 |
|---|---|---|---|---|---|---|---|
| ADR-001 | 2026-03-04 | 검색을 DB 문자열 부분일치로 구현 | ① 색인 엔진 ② 형태소 분석기 | 장서 수천 건에서 `FR-LIB-01`이 충족되고 운영 요소가 늘지 않는다 | 수십만 건이면 선형으로 느려지고 오탈자 보정이 없다 | `NFR-LIB-01` 측정값이 승인 합격값을 넘을 때 | Active |
| ADR-002 | 2026-03-04 | 결과 0건과 조회 실패를 다른 응답으로 구분 | 둘 다 빈 목록으로 반환 | `FR-LIB-02`의 금지 해석을 화면이 지키려면 둘을 구별할 수 있어야 한다 | 호출부가 두 경우를 모두 다뤄야 한다 | 없음(불변조건에 가깝다) | Active |

**부적합한 ADR**

| ✗ | 문제점 |
|---|---|
| 검토한 대안이 비어 있다 | 기각 기록이 없으면 6개월 뒤 같은 대안을 다시 실험한다 |
| 선택 이유가 "그게 더 좋아서" | 어떤 요구를 충족하는지 또는 어떤 비용을 피하는지를 써야 한다 |
| 되돌릴 조건이 비어 있다 | 재검토 시점이 영원히 오지 않는다 |

## 5. 금지 사항

- 함수 본문·설정값 나열 등 코드 복제
- 시장 분석·사용자 스토리의 반복(상위 문서 참조로 대체)
- 시험 절차(TC 영역)
- 검증되지 않은 성능 주장, 이유 없는 결정("~가 좋아서")
- 조건이 생기지 않았는데 미리 만들어 두는 빈 절(§3.2의 추가 조건을 먼저 확인)
- SRS가 소유한 요구·합격값의 재서술 — 여기서는 그것을 **실현하는 구조**만 쓴다

## 6. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] 모든 ADR 행에 여덟 칸이 다 채워져 있다
      (날짜·결정·대안·이유·비용·되돌릴 조건·상태 중 빈 칸이 있는 행 0개)
- [ ] 검토한 대안이 "없음"이 아니다 (대안 없는 결정은 결정이 아니라 제약이다)
- [ ] 결정 이력이 보존된다
      (바뀐 결정의 행이 삭제되지 않고 `Superseded(→ADR-0NN)`로 남아 있는지 확인)
- [ ] 코드 본문 복사가 없다
      (코드 블록을 전부 열어 함수 본문·조건문·반복문이 들어 있으면 지운다.
      남길 수 있는 것은 mermaid 다이어그램과 파일 경로뿐)
- [ ] 각 설계 요소가 SRS의 FR 또는 NFR과 연결된다 (추적 표에 빠진 절 0개)
- [ ] 빈 절이 없다
      (§3.2의 추가 조건을 만족하지 않는 절이 만들어져 있으면 삭제)
- [ ] 검증 안 된 내용이 검증된 것처럼 서술되지 않았다
      (근거 미확인은 `근거 미기록`, 실행 미검증은 `실행 검증 필요` 표기)

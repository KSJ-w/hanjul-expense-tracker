# SRS 작성 가이드 (SRS_guide)

> SRS(Software Requirements Specification, 소프트웨어 요구사항 명세서)는
> **"시스템이 무엇을 얼마나 정확히 보장해야 하는가"**를 검증 가능하게 확정한다.
> 체인에서 가장 공학적인 문서이고, 모든 시험(TC)의 직접 입력이다.
> 공통 규칙은 [README.md](README.md)를 따른다.

## 1. 입력과 출력

- **입력**: 확정된 RFP·PRD
- **출력**: 검증 가능한 기능 요구(**RFP의 FR·NFR 번호를 그대로 유지**), 비기능 요구,
  인터페이스 계약, 시스템 불변조건, 상태·오류 의미, 요구별 검증 유형
- **다음 문서**: TC가 각 요구를 시험 절차로 전개한다. SDD가 이 요구를 실현하는
  설계를 기록한다

## 2. FR·NFR 번호 관통 규칙

SRS는 **새 요구 번호를 만들지 않는다.** RFP에서 태어난 `FR-<COMP>-NN`과
`NFR-<COMP>-NN`을 같은 번호로 유지하면서 두 가지만 더한다.

1. 문구를 **관찰·측정·판정 가능**하게 정련한다
2. **검증 유형**을 붙인다 — 시험(Test) · 검사(Inspection) · 시연(Demonstration) · 분석(Analysis)

정련 예시. **번호는 그대로 유지되며, 추가되는 것은 관찰 지점과 검증 유형이다.**

| ID | RFP의 문장 | SRS의 문장 |
|---|---|---|
| `FR-LIB-01` | 입력 키워드와 일치하는 도서를 관련도 순으로 반환해야 한다 \| M | 입력 키워드를 **제목·저자와 대조**해 일치한 도서만 **관련도 내림차순**으로 반환해야 한다 \| M \| **시험** |
| `FR-LIB-02` | 결과가 없을 때 장서에 없다는 뜻으로 표시해서는 안 된다 \| M | **결과가 0건일 때** 장서 부재를 단정하는 문구를 표시해서는 안 된다 \| M \| **시험** |
| `NFR-LIB-01` | 검색 결과가 담당자를 기다리게 하지 않아야 한다 \| S | 검색 **요청 수신부터 결과 응답까지**의 시간을 측정할 수 있어야 한다 \| S \| 합격값 **미승인** \| **시험** |

SRS에서 처음 발견된 요구(데이터·보안 등)는 RFP에 먼저 FR·NFR로 추가한 뒤
가져온다. 여기서 새 번호를 만들면 추적성이 그 지점에서 끊긴다.

## 3. 문서 골격

```
헤더 표: 문서 역할 · 버전 · RFP/PRD 기준(버전 링크) · 상태(Draft)
## 1. 목적·범위·용어      1.1 목적 / 1.2 문서 경계 표(내용|소유 문서)
                         1.3 규범 용어(SHALL=충족 필수, SHOULD=목표, MAY=선택)
                         1.4 핵심 용어집 표 — 프로젝트 고유 용어를 빠짐없이 정의
## 2. 기능 요구사항       FR 표(RFP §5와 같은 그룹 구성 유지):
                         | ID | 요구(검증 가능 문형) | 우선순위 | 검증 유형 |
## 3. 비기능 요구사항     `NFR-<COMP>-NN` — 성능·신뢰성·**보안**·사용성·유지보수성
                         표: | ID | 요구 | 우선순위 | 측정 대상 | 관찰 시작·종료점 |
                             | 합격값 | 승인 상태 | 검증 유형 |
                         측정·승인 전이면 합격값을 비우고 승인 상태를 `미승인`으로 둔다.
                         **합격선은 이 표가 소유한다** — TC는 인용만 하고 새로 만들지 않는다
## 4. 시스템 불변조건     번호 목록(보통 3~7개) — 어떤 구현에서도 깨지면 안 되는 규칙
                         (예: "빈 결과를 대상 부재로 표시하지 않는다")
## 5. 인터페이스 계약     기능군 수준 표: 행위자|입력·validation|성공 의미|오류 의미
                         ※ 정확한 endpoint·payload 필드는 복제하지 않는다(설계 소유)
## 6. 상태·오류·빈 결과 의미   표: 상황|시스템 판정|사용자에게 표시할 의미|
                         **금지되는 해석**|가능한 다음 행동
## 7. 데이터 논리 계약    저장 기술과 무관하게 보존할 식별·귀속·참조 관계
                         (물리 스키마·인덱스는 SDD 소유)
## 8. 비목표와 호환 경로  현재 요구가 아닌 것 / 과거 호환용의 명시적 분리
## 9. 제약과 가정         표: | 구분(제약/가정) | 내용 | 근거 | 깨지면 무효가 되는 요구 |
                         "이 요구들이 어떤 전제 위에서 성립하는가". 가정을 적지 않으면
                         전제가 깨졌을 때 요구가 틀린 것인지 전제가 틀린 것인지 알 수 없다
## 10. 추적성            표 위에 체인 한 줄:
                         `MRD → RFP(FR·NFR) → PRD(US) → **SRS**(같은 번호) → TC → test`
                         | RFP FR·NFR | 본 SRS(같은 번호) | PRD US | 하위 TC(예정) |
                         표 아래에 **검수 합계 한 줄**을 남긴다(§6에서 센 숫자)
## 11. 변경 이력         | 버전 | 날짜 | 변경 요약 | 영향 요구(FR·NFR ID) |
## 12. 미결 사항         | ID | 질문 | 영향 | 상태(Open/Decided) | 결정 |
```

## 4. 작성 규칙

- **원자성**: 요구 하나 = 판정 하나. "A하고 B해야 한다"는 판정이 반쪽 날 수
  있으므로 쪼갠다.
- **검증 가능 문형**: 확인할 방법이 없는 문장("빨라야 한다", "쉬워야 한다")은
  요구가 아니다. 관찰 지점과 판정 조건이 문장 안에 있어야 한다.
- **오류의 의미를 고정한다**: 인증 실패·권한 부족·입력 오류·자원 없음·충돌의
  구분(예: 401/403/422/404/409 의미)과 각각의 부작용 없음을 명시한다.
- **금지되는 해석을 명시한다**: "결과 없음 ≠ 대상 없음", "낮은 점수 ≠ 불일치
  확정"처럼 시스템이 표시하면 안 되는 해석을 §6에 적는다.
- **수치는 승인된 것만 합격선으로**: 측정·승인 전 수치는 승인 상태를 `미승인`으로
  적고 합격 기준에 넣지 않는다.
- **서술과 요구를 구분한다**: 의무는 "~해야 한다(SHALL)", 목표는 "~하는 것을
  목표로 한다(SHOULD)", 선택은 "~할 수 있다(MAY)". 평서문("~한다")은 요구가
  아니라 설명이므로 요구 표에 넣지 않는다.
- 모든 요구는 검증 유형 4종 중 하나 이상으로 확인 가능해야 한다. 자동 시험이
  불가능한 요구(문구 검토, 사용자 시연)는 유형을 정직하게 검사/시연으로 둔다.
- **검사·시연·분석으로 분류하려면 이유를 한 줄 적는다**: "왜 시험으로 만들 수
  없는가"를 쓰지 않으면, 자동화가 귀찮아서 회피한 것과 구분되지 않는다.
- **합격선은 §3이 소유한다**: 수치 합격값은 비기능 요구 표에만 존재하고, TC는
  그 값을 인용한다. TC에서 처음 등장하는 수치는 근거 없는 합격선이다.

### 부적합한 요구 문장

- ✗ 검색이 **빨라야** 한다 → 관찰 지점과 판정 조건이 없다. 측정 시작·종료
  시점이 문장에 드러나지 않는다
- ✗ 시스템은 결과를 반환**하고** 이력을 기록해야 한다 → 반쪽만 충족될 수 있다.
  두 요구로 쪼갠다
- ✗ 시스템은 결과를 반환**한다** → 평서문. 의무인지 설명인지 알 수 없다

## 5. 금지 사항

- 새 FR·NFR 번호 발급(요구가 새로 필요하면 RFP에 먼저 추가)
- `AT`·`SR` 같은 새 ID 가족 신설 — 합격선은 §3의 비기능 요구 표가 소유한다
- 기술 선택 이유, 코드 구성, 배포 구조(SDD 영역)
- 시험 절차·fixture(TC 영역)
- 구현 상태 표기(README §5) / 미승인 수치의 합격선화
- 사용자 스토리의 반복 서술(PRD 참조로 대체)

## 6. 완료 체크리스트

괄호의 판별 방법으로 **실제로 검사**한다. 눈으로 훑고 체크하지 않는다.

- [ ] 모든 FR·NFR 번호가 RFP와 동일하고, SRS에서 새 번호를 만들지 않았다
      → 센 결과를 골격 §10 합계 줄에 적는다: `SRS에만 있는 ID __개` (0이어야 한다)
- [ ] RFP의 모든 Active FR·NFR이 빠짐없이 정련됐다
      → 센 결과를 골격 §10 합계 줄에 적는다: `RFP __개 / SRS __개 / RFP에만 있는 ID __개`
- [ ] 모든 요구에 우선순위와 검증 유형이 붙어 있다 (빈 칸 0개)
- [ ] 검사·시연·분석으로 분류한 요구에 그 이유가 적혀 있다
- [ ] 모든 요구가 원자적이다
      ("그리고"·"하며"·"및"을 검색해 걸린 행을 하나씩 재검토)
- [ ] 모든 요구가 SHALL/SHOULD/MAY 문형이다 (평서문 "~한다"로 끝나는 요구 0개)
- [ ] 관찰 지점 없는 표현이 없다
      ("빠르게"·"쉽게"·"안정적으로"·"적절히"를 검색해 0건인지 확인)
- [ ] 오류·빈 결과의 의미와 **금지되는 해석**이 정의됐다 (골격 §6)
- [ ] 합격값이 적힌 요구는 승인 상태가 `승인`이다
      (`미승인`인 값이 TC 합격선으로 넘어가지 않게 확인)
- [ ] 본문에 쓴 프로젝트 고유 용어가 빠짐없이 용어집에 있고, 문서 전체에서
      같은 뜻으로 쓰인다
- [ ] 요구가 성립하는 전제가 §9 제약과 가정에 적혀 있다
